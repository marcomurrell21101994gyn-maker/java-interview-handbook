1. HashMap 在 JDK8+ 的结构是什么？

【答】
可以把它想成两层：

  1. 外面一层是数组：每个位置叫一个「桶」，用来快速落到某一格。
  2. 桶里面才是真正的数据：正常是一个节点；多个 key 落到同一桶（冲突）就串成链表；串得特别长再改成红黑树。

JDK8 往链表尾巴挂新节点（尾插）。在 hash 分布比较均匀、冲突不严重时，平均查找接近 O(1)。

【展开】 ① 结构图（数组是一排桶，不是树）

flowchart TB subgraph arr["table 桶数组"] direction LR b0["0"] --- b1["1"] --- b2["2"] --- b3["…"] --- bn["n-1"] end b1 --> p1["Node k1"] --> p2["Node k2"] --> p3["Node k3"] b2 --> r["红黑树根"] r --> rl[左子] r --> rr[右子]

② 为什么要数组？
按「算出来的下标」一步跳到桶，比从头扫列表快。

③ 冲突

flowchart TD K[key] --> H[算出桶下标 i] H --> D{table i 是否为空} D -->|空| P[放入新 Node] D -->|非空| C[同一桶内：链表串起来 或进树]

④ 下标怎么来
key → 整数 hash（含扰动）→ 映射到 0 ~ 桶数-1（桶数是 2 的幂时用位运算取模）。

2. HashSet 底层是什么？

【答】
HashSet 自己几乎没数据结构，内部就是一个 HashMap：
你 add 的元素当 key，value 用一个固定占位对象。
所以「能不能加进去」完全看 HashMap 的 key 是否已存在。

【展开】

flowchart LR SET[HashSet] --> MAP[内部 HashMap] MAP --> REC["存放形式：你的元素 作为 key → 固定占位作为 value"]
flowchart TD A1["第一次 add x"] --> OK["map 里没有 x → 放进去"] A2["再次 add x"] --> NO["map 里已有 x → 加不进去"]

面试连带结论：复杂度、是否线程安全，都跟 HashMap 同一套说法。

高频追问：HashSet 怎么判断重复？
不是只看 hashCode()，也不是只看 equals()，而是先用 hashCode() 定位桶，再用 equals() 判断是否真相等。自定义对象放 HashSet 时，要同时重写 equals() 和 hashCode()。细节见题 11。

3. ArrayList 和 LinkedList 有什么区别？怎么选？

【答】

  • ArrayList：连续数组，按下标读很快。
  • LinkedList：链表，按下标要一个个爬，慢。
  • 怎么选：默认 ArrayList；真要双端队列优先想 ArrayDeque，别习惯性写 LinkedList。

【展开】

flowchart TB subgraph A["ArrayList"] direction LR x0["a"] --- x1["b"] --- x2["c"] --- x3["d"] end subgraph L["LinkedList"] direction LR y0[a] --> y1[b] --> y2[c] --> y3[d] end
ArrayList LinkedList
读第 i 个 快 O(1) 慢 O(n)
尾部追加 通常快 也快
中间插入 要挪后面元素 若已拿到节点才快；先按索引找仍慢

常见坑：以为「增删就用 LinkedList」——你还没拿到节点之前，一样慢。

补充：ArrayList 底层数组容量不够时会扩容，常见是扩到原来的 1.5 倍左右，并复制旧数组。细节见题 10。

4. HashMap 的 put 过程是怎样的？

【答】
面试按这条线说就够（不用背树的旋转）：

  1. 算出下标，找到桶
  2. 桶空 → 直接放；key 已存在 → 覆盖 value
  3. 否则挂到链表（或树）里
  4. 插入后 size 增加，超过阈值就扩容；桶内链表够长时再考虑树化

【展开】

flowchart TD A["put k,v"] --> B[算桶下标] B --> C{桶空?} C -->|是| D[直接放] C -->|否| E{同 key?} E -->|是| F[覆盖 value] E -->|否| G[尾插或进树] D --> H{要树化或扩容?} F --> H G --> H H --> I[结束]

追问才补：扩容通常看 size > threshold，threshold = capacity * loadFactor，默认负载因子是 0.75；树化要「够长 + 数组够大」。细节见题 5、题 7。

5. 扩容时元素怎么迁移？

【答】
容量翻倍时，JDK8 不会重新算一遍 hash。
每个元素只可能留在原下标，或搬到 原下标 + 旧容量。然后拆成两条链挂回去。

【展开】

flowchart TB subgraph before["扩容前 容量=16 全在桶1"] direction LR s1[stayA] --> m1[moveC] --> s2[stayB] --> m2[moveD] end subgraph after["扩容后 容量=32"] direction TB subgraph b1["桶1 留下"] direction LR s1b[stayA] --> s2b[stayB] end subgraph b17["桶17 = 1+16 搬过去"] direction LR m1b[moveC] --> m2b[moveD] end end before --> after

为什么可以这么省事？容量是 2 倍关系，新下标只多看「多出来的那一位」是 0 还是 1。

面试追问版：判断依据是 hash & oldCap。
结果为 0，留在原下标；结果不为 0，移动到 原下标 + oldCap。

补充：JDK7 并发扩容有「成环」的历史故事；今天主答案仍是——HashMap 本身不保证线程安全。

6. ConcurrentHashMap 怎么保证并发安全？（JDK8+）

【答】
JDK8+ 记住两句：

  1. 空桶：常用 CAS 抢着放，尽量少加锁。
  2. 桶里已有链/树：锁住这个桶的头，别的桶还能并行写。
  3. 读操作：get 通常不加锁，依赖 volatile 等机制保证可见性，所以读性能比较好。

业务上「先判断再 put」要换成 putIfAbsent / compute / merge 这类原子方法。
（「分段锁」是 JDK7 的说法，别当现代主答案。）

7. 为什么要树化？

【答】
链表太长，查找会从 O(1) 退化成接近 O(n)。树化是为了把最坏情况压住。
不是「到 8 个就树」：还要数组长度至少 64；表还小的时候优先扩容拆散，更划算。

【展开】

flowchart TB subgraph chain["树化前：同一桶链表"] direction LR c1[N1] --> c2[N2] --> c3[N3] --> c4[N4] end subgraph tree["树化后：同一桶红黑树"] r[根] --> l[左] r --> ri[右] l --> ll[…] ri --> rr[…] end chain -->|条件满足| tree

看图重点：HashMap 的桶里一开始可能是链表，链表太长且数组够大时，才会转成红黑树。

条件 含义
单桶节点达到 8 左右 这条链已经够长，触发树化判断
数组长度 ≥ 64 表够大，值得养树
表还小 先扩容，往往链就散了

常见追问：树一定不会退回链表吗？
不是。节点少到一定程度时，红黑树可能会退化回链表。面试记住三个关键词即可：8 左右尝试树化，64 以前优先扩容，节点变少可能退化。

8. table 容量为什么是 2 的幂？

【答】
两件事更简单：

  1. 用位运算快速得到桶下标（等价取模）
  2. 扩容翻倍时，元素只在「原地 / 原地+旧容量」两种去向

你传入的初始容量不必是 2 的幂，内部会抬成 2 的幂。

9. HashMap 为什么线程不安全？

【答】
多线程一起 put，可能丢数据，也可能把内部结构写乱。
所以并发场景直接用 ConcurrentHashMap。
JDK7「扩容死循环」是加分追问，不要当成今天唯一答案。

10. ArrayList 是怎么扩容的？

【答】
ArrayList 底层是数组。数组容量不够时，会创建一个更大的新数组，再把旧数组里的元素复制过去。

JDK8 常见扩容比例大约是 1.5 倍。所以 ArrayList 尾部追加通常很快，但一旦触发扩容，就会有一次数组复制成本。

【展开】

flowchart LR subgraph old["旧数组 容量=4 已满"] direction LR a0[a] --- a1[b] --- a2[c] --- a3[d] end subgraph new["新数组 容量变大"] direction LR b0[a] --- b1[b] --- b2[c] --- b3[d] --- b4[e] --- b5[空] end old -->|扩容 + 复制| new

面试这样说就够：

  1. ArrayList 底层是数组。
  2. 容量不够时创建新数组。
  3. 新容量通常约为旧容量的 1.5 倍。
  4. 旧元素复制到新数组。
  5. 所以频繁扩容会有成本，能预估大小时可以指定初始容量。

常见追问：为什么建议指定初始容量？

如果一开始就知道大概要放多少元素，指定容量可以减少扩容次数和数组复制成本。

11. HashSet 如何判断元素重复？

【答】
HashSet 底层用 HashMap，所以判断重复本质上是判断 HashMap 的 key 是否已经存在。

判断过程可以简单记成两步：

  1. 先用 hashCode() 算位置。
  2. 如果位置上已有元素，再用 equals() 判断是否真的相等。

所以自定义对象放进 HashSet 时，必须正确重写 hashCode() 和 equals()。

【展开】

flowchart TD A["add(obj)"] --> B["调用 obj.hashCode()"] B --> C["定位到桶"] C --> D{桶里有没有元素?} D -->|没有| E["直接放入"] D -->|有| F["逐个用 equals() 比较"] F --> G{equals 为 true?} G -->|是| H["认为重复，不添加"] G -->|否| I["不重复，添加进去"]

面试重点：

方法 作用
hashCode() 决定大概放到哪个桶
equals() 判断两个对象内容是否真的相等

常见坑：

只重写 equals，不重写 hashCode，可能导致内容相同的对象落到不同桶里，HashSet 判断不出重复。

一句话总结：

HashSet 去重不是只靠 equals，也不是只靠 hashCode，而是两者配合。

1. JVM 运行时数据区有哪些？哪些是线程私有的？

【答】
JVM 运行时数据区可以分成两类：

  1. 线程私有：程序计数器、虚拟机栈、本地方法栈。
  2. 线程共享：堆、方法区。

面试中重点记住：堆是对象主要存放区域，栈是方法调用和局部变量区域，方法区存类信息。

【展开】

flowchart TB JVM["JVM 运行时数据区"] JVM --> P["线程私有"] JVM --> S["线程共享"] P --> PC["程序计数器"] P --> Stack["虚拟机栈"] P --> Native["本地方法栈"] S --> Heap["堆"] S --> Method["方法区 / 元空间"]

看图重点：堆、方法区是线程共享的；程序计数器、虚拟机栈、本地方法栈是线程私有的。

区域 是否线程私有 主要放什么
程序计数器 是 当前线程执行到哪一行字节码
虚拟机栈 是 栈帧、局部变量、操作数栈、方法返回地址
本地方法栈 是 Native 方法调用相关
堆 否 对象实例、数组
方法区 否 类元数据、运行时常量池、即时编译后的代码等

常见追问：方法区是不是永久代？

方法区是 JVM 规范里的概念。
永久代是 HotSpot 早期对方法区的一种实现。
JDK8 以后，永久代被元空间替代，元空间使用本地内存。

面试注意：

不要把“方法区、永久代、元空间”混成一个东西。
方法区是规范概念，永久代和元空间是 HotSpot 不同版本的实现。
静态字段和 Class 对象的具体存放实现细节，不建议初学阶段讲太死，面试主线说“类相关信息由方法区/元空间管理”更稳。

2. 堆、栈、方法区分别存什么？

【答】
一句话记：

  • 堆：放对象。
  • 栈：放方法调用过程。
  • 方法区：放类相关信息。

【展开】

flowchart LR A["new User()"] --> Heap["堆：User 对象"] B["main 方法调用"] --> Stack["栈：栈帧/局部变量"] C["User.class"] --> Method["方法区：类信息/方法信息"]

例子：

User user = new User();

可以这样理解：

new User() 创建出来的对象在堆里。
user 这个局部变量在当前方法的栈帧里。
User 类的类信息在方法区/元空间里。

注意：不要简单说“对象一定都在堆上”。JIT 优化后可能有逃逸分析、栈上分配、标量替换等优化。面试普通回答说“对象主要分配在堆上”更稳。

3. 类加载器有哪些？双亲委派机制是什么？

【答】
常见类加载器：

  1. Bootstrap ClassLoader：加载 Java 核心类库。
  2. Extension / Platform ClassLoader：加载平台扩展类。
  3. Application ClassLoader：加载应用 classpath 下的类。
  4. 自定义 ClassLoader：框架或容器自定义加载逻辑。

双亲委派就是：一个类加载请求先交给父加载器，父加载器加载不了，子加载器才自己加载。

【展开】

flowchart TB B["Bootstrap ClassLoader"] P["Platform / Extension ClassLoader"] A["Application ClassLoader"] C["自定义 ClassLoader"] C --> A --> P --> B

看图重点：类加载请求先向上委派，父加载器加载不了，才由子加载器尝试加载。

为什么要双亲委派？

保护核心类，避免用户自己写一个 java.lang.String 把 JDK 核心类替换掉。
保证类加载的稳定性和安全性。

常见追问：双亲委派一定不能打破吗？

不是。像 Tomcat、SPI、某些热部署和插件化场景，会有自己的类加载机制。
但面试主线先讲双亲委派，再说特殊场景会打破。

5. Java 对象是怎么创建的？对象一般分配在哪里？

【答】
对象创建大致流程：

  1. 检查类是否已加载。
  2. 给对象分配内存。
  3. 初始化零值。
  4. 设置对象头。
  5. 执行构造方法。

对象一般分配在堆上，优先在 Eden 区。

【展开】

flowchart LR A["new 对象"] --> B["检查类加载"] B --> C["分配内存"] C --> D["初始化零值"] D --> E["设置对象头"] E --> F["执行构造方法"]

常见分配路径：

大多数新对象 → Eden 区
Eden 放不下 → 触发 Minor GC
长期存活对象 → 晋升老年代
大对象 → 可能直接进入老年代

面试不用把 TLAB、逃逸分析讲太深，但可以补一句：

为了提高分配效率，JVM 可能给线程分配 TLAB，减少多线程竞争。

6. JVM 如何判断对象是否可以被回收？

【答】
主流 JVM 使用可达性分析判断对象是否可回收。

从一组 GC Roots 出发往下找，能找到的对象就是存活对象；找不到的对象，就是不可达对象，可能被回收。

【展开】

flowchart TB R["GC Roots"] --> A["对象A"] A --> B["对象B"] X["对象X"] --> Y["对象Y"] R -. "找不到" .-> X

图里：

  • 对象 A、B 从 GC Roots 能到达，不能回收。
  • 对象 X、Y 从 GC Roots 到不了，可能回收。

为什么不用引用计数法？

引用计数法处理不了循环引用。
两个对象互相引用，但外部已经访问不到，也应该被回收。

7. 什么是可达性分析？GC Roots 有哪些？

【答】
可达性分析就是从 GC Roots 开始，沿着引用链向下搜索，判断对象是否还“活着”。

常见 GC Roots：

  1. 虚拟机栈中的引用。
  2. 方法区中静态变量引用的对象。
  3. 方法区中常量引用的对象。
  4. 本地方法栈中 Native 方法引用的对象。
  5. 当前被同步锁持有的对象等。

【展开】

flowchart LR S["栈中局部变量"] --> O1["对象1"] Static["静态变量"] --> O2["对象2"] Const["常量引用"] --> O3["对象3"] Native["Native 引用"] --> O4["对象4"]

看图重点：从 GC Roots 能连上的对象是存活对象，连不上的对象才可能被回收。

面试表达：

GC Roots 可以理解为垃圾回收扫描的起点。
从这些起点能访问到的对象，就认为还在使用。
访问不到的对象，才有机会被回收。

8. 垃圾回收算法有哪些？

【答】
常见垃圾回收算法有：

  1. 标记-清除
  2. 标记-整理
  3. 复制算法
  4. 分代收集

【展开】

算法 思路 优点 缺点
标记-清除 标记垃圾，再清掉 简单 容易产生内存碎片
标记-整理 标记后把存活对象整理到一边 减少碎片 移动对象成本高
复制算法 把存活对象复制到另一块空间 适合存活对象少的区域 浪费一部分空间
分代收集 新生代、老年代用不同算法 更符合对象生命周期 实现复杂

为什么要分代？

大部分对象朝生夕死，少部分对象活很久。
新生代适合复制算法，老年代更适合标记-整理或类似算法。

9. 常见垃圾回收器有哪些？G1 为什么常用？

1. synchronized 的底层原理是什么？

【答】
synchronized 是 Java 内置锁，用来保证同一时刻只有一个线程进入临界区。

它有两种常见用法：

  1. 修饰普通方法或普通代码块：锁的是当前对象。
  2. 修饰 static 方法或 Class 代码块：锁的是这个类的 Class 对象。

底层主要依赖对象头中的 Mark Word 和 Monitor 机制。

【展开】

public synchronized void add() {
    count++;
}

这段代码的意思是：

线程进入 add 方法前，先尝试拿到当前对象的锁。
拿到锁才能执行 count++。
执行完方法后自动释放锁。

同步代码块底层会用到：

monitorenter
monitorexit

可以简单理解成：

monitorenter：进入时加锁
monitorexit：退出时解锁

锁对象怎么判断：

写法 锁对象
synchronized void method() 当前对象 this
synchronized static void method() 当前类的 Class 对象
synchronized (obj) 括号里的 obj
synchronized (User.class) User.class

常见追问：synchronized 有什么特点？

可重入：同一个线程拿到锁后，可以再次进入同一把锁保护的代码。
自动释放：方法结束或异常退出都会释放锁。
不可中断：线程等 synchronized 锁时，不能像 ReentrantLock 那样主动中断等待。
非公平：不保证先等待的线程一定先拿到锁。

面试注意：

不要只背“无锁、偏向锁、轻量级锁、重量级锁”。
现代 JDK 中偏向锁已经不是重点，主线应该放在 monitor、可重入、互斥、可见性和竞争成本。

一句话总结：

synchronized 是 Java 内置互斥锁，简单、安全、自动释放，适合大多数普通同步场景。

2. volatile 的作用是什么？能不能保证原子性？

【答】
volatile 主要解决两个问题：

  1. 可见性：一个线程修改变量后，其他线程能及时看到。
  2. 有序性：限制指令重排序。

但是 volatile 不能保证复合操作的原子性。

【展开】

private volatile boolean running = true;

这种变量适合做状态标记：

线程 A 修改 running = false
线程 B 能及时看到 running 变成 false

但是下面这段代码不安全：

private volatile int count = 0;

public void add() {
    count++;
}

原因是 count++ 不是一步完成的：

读取 count
加 1
写回 count

多个线程同时执行时，还是可能互相覆盖。

flowchart LR A["读 count"] --> B["加 1"] B --> C["写回 count"]

面试重点：

能力 volatile 是否支持
可见性 支持
有序性 支持
原子性 不支持

常见使用场景：

状态开关
停止标记
双重检查锁中的单例对象引用

一句话总结：

volatile 不是锁，它适合做状态可见性控制，不适合保护 count++ 这种复合更新。

3. synchronized 和 ReentrantLock 有什么区别？

【答】
两者都能实现互斥，但使用方式和能力不同。

synchronized 是关键字，使用简单，自动释放锁。

ReentrantLock 是 JUC 提供的锁对象，功能更灵活，但必须手动释放锁。

【展开】

对比点 synchronized ReentrantLock
类型 Java 关键字 JUC API
释放锁 自动释放 必须手动 unlock()
可重入 支持 支持
公平锁 不支持指定公平策略 支持公平 / 非公平
可中断等待 不支持 支持
超时获取锁 不支持 支持 tryLock
条件队列 一个等待队列 可创建多个 Condition
底层 Monitor AQS

标准写法：

Lock lock = new ReentrantLock();

lock.lock();
try {
    // 业务代码
} finally {
    lock.unlock();
}

为什么一定要放在 finally 里？

如果业务代码抛异常，finally 仍然会执行 unlock。
否则锁可能一直不释放，其他线程就会一直等。

怎么选？

普通同步：优先 synchronized，简单、不容易写错。
需要可中断、超时、公平锁、多个 Condition：选择 ReentrantLock。

一句话总结：

synchronized 胜在简单安全，ReentrantLock 胜在功能更强，但使用时必须手动释放。

4. AQS 是什么？ReentrantLock 怎么基于 AQS 实现？

【答】
AQS 全名是 AbstractQueuedSynchronizer，可以理解为 JUC 锁和同步器的底层骨架。

它的核心就两样东西：

  1. 一个 volatile int state：表示同步状态。
  2. 一个等待队列：抢不到锁的线程会进队列等待。

【展开】 在 ReentrantLock 中：

state = 0：锁没人持有
state = 1：锁被某个线程持有
state > 1：同一个线程重入了多次

抢锁过程：

flowchart TD A["线程调用 lock()"] --> B{"CAS 抢 state 成功?"} B -->|成功| C["成为持锁线程"] B -->|失败| D["进入 AQS 等待队列"] D --> E["线程 park 挂起"] C --> F["执行业务"] F --> G["unlock 释放锁"] G --> H["唤醒队列里的后继线程"]

可以这样理解：

state 负责记录“锁有没有被占用”。
队列负责管理“没抢到锁的人怎么排队”。

常见基于 AQS 的组件：

组件 state 表示什么
ReentrantLock 锁的重入次数
ReentrantReadWriteLock 读锁数量和写锁重入次数
CountDownLatch 还剩多少次倒计数
Semaphore 还剩多少许可证

公平锁和非公平锁：

非公平锁：新来的线程可以先尝试抢锁，吞吐量高，但可能插队。
公平锁：先看队列里有没有前驱节点，有就排队，等待更有秩序，但性能通常低一些。

一句话总结：

AQS 把“抢资源”抽象成 state，把“等资源”抽象成队列，ReentrantLock 就是基于它实现的。

5. CAS 是什么？有什么问题？

【答】
CAS 全名是 Compare And Swap，中文可以理解成“比较并交换”。

它的逻辑是：

如果当前值还是我预期的旧值，就更新成新值。
如果当前值已经变了，就更新失败。

CAS 属于乐观锁思想。

【展开】 CAS 有三个关键值：

值 含义
V 内存中的当前值
A 预期旧值
B 要更新的新值

过程：

如果 V == A，就把 V 改成 B。
如果 V != A，说明被别人改过，本次更新失败。
flowchart LR A["读取当前值 V"] --> B{"V 是否等于预期值 A?"} B -->|是| C["更新为新值 B"] B -->|否| D["更新失败，重试或放弃"]

常见应用：

AtomicInteger
AtomicLong
AtomicReference
ConcurrentHashMap
AQS 抢 state

CAS 的问题：

问题 说明
ABA 问题 值从 A 变成 B，又变回 A，CAS 以为没变过
自旋开销 一直失败就会一直重试，CPU 消耗变高
只能保证单个变量更新 多个变量一起保持一致时会复杂

ABA 怎么解决？

给值加版本号。
比如 AtomicStampedReference，不只比较值，还比较版本号。

一句话总结：

CAS 不加传统互斥锁，而是靠“比较旧值再更新”实现原子修改，适合竞争不太激烈的场景。

6. 什么是死锁？怎么排查？

【答】
死锁就是多个线程互相等对方释放锁，结果谁也走不下去。

最常见的情况是：

线程 A 拿着锁 1，等锁 2。
线程 B 拿着锁 2，等锁 1。
两个线程互相等待，程序卡住。

【展开】

flowchart TB A["线程 A"] --> L1["已持有锁 1"] A --> W2["等待锁 2"] B["线程 B"] --> L2["已持有锁 2"] B --> W1["等待锁 1"] W2 --> B W1 --> A

死锁通常需要同时满足四个条件：

条件 大白话解释
互斥 锁一次只能被一个线程拿到
请求并保持 拿着一把锁不放，又去申请另一把锁
不可抢占 别人不能强行把锁抢走
循环等待 多个线程形成互相等待的圈

传统排查方式：

jps
jstack <pid> > thread.txt

然后在 thread.txt 里看：

Found one Java-level deadlock

如果出现这类信息，说明 JVM 已经检测到了 Java 层面的死锁。

Arthas 排查方式：

dashboard
thread -b

其中：

命令 作用
dashboard 先看应用整体状态
thread -b 找出当前阻塞其他线程的线程

怎么避免死锁？

固定加锁顺序。
减少锁嵌套。
使用 tryLock 设置超时时间。
避免锁内执行慢 IO、远程调用或复杂业务。

一句话总结：

死锁不是靠猜，先用 jstack 或 Arthas 找线程栈，再看锁的持有和等待关系，最后回到代码调整加锁顺序。

1. 进程和线程有什么区别？

【答】
进程是系统分配资源的基本单位，线程是 CPU 调度执行的基本单位。

简单说：

进程像一个正在运行的应用。
线程像应用里真正干活的人。

【展开】

对比点 进程 线程
定位 资源分配单位 CPU 调度单位
内存 进程之间内存相对独立 同一进程内线程共享堆内存
通信成本 较高 较低
崩溃影响 一个进程崩溃通常不直接影响其他进程 普通线程未捕获异常通常只会结束该线程，但关键线程异常、资源污染或严重 Error 可能影响整个服务

Java 程序启动后，JVM 本身就是一个进程。

这个进程里会有很多线程，例如：

main 主线程
GC 线程
业务线程
线程池工作线程
监控线程

面试表达：

进程拥有独立资源，线程共享进程资源。
多线程提高并发能力，但共享数据也会带来线程安全问题，所以需要锁、原子类、线程池等机制。

一句话总结：

进程负责装资源，线程负责执行代码；线程共享资源，所以才会有并发安全问题。

2. Java 中创建线程/提交任务有哪些方式？

  2. 实现 Runnable。
  3. 实现 Callable，配合 Future 获取返回值。

线程创建和销毁有成本。

Runnable 和 Callable 的区别：

JDK21 以后虚拟线程适合大量阻塞 IO 场景，比如大量 HTTP 调用、数据库等待。
但它不是万能的，数据库连接池、下游限流、超时控制仍然必须做。

一句话总结：

创建线程的方式会背，但生产更关注任务如何交给线程池管理，而不是手动乱建线程。

4. 什么是线程安全？为什么会出现线程安全问题？

【答】
线程安全就是：多个线程同时操作同一份数据时，程序结果仍然正确。

线程安全问题通常来自三个条件同时出现：

多个线程
共享数据
至少一个线程会修改数据

【展开】 例子：

private int count = 0;

public void add() {
    count++;
}

count++ 看起来是一行，实际不是一步：

读取 count
加 1
写回 count

多个线程同时执行时，可能出现：

线程 A 读到 count=0
线程 B 也读到 count=0
线程 A 写回 1
线程 B 也写回 1
本来加了两次，结果只加成 1
flowchart LR A["线程 A 读取 0"] --> B["线程 A 写回 1"] C["线程 B 读取 0"] --> D["线程 B 写回 1"] B --> E["最终结果 1"] D --> E

并发安全常见问题：

问题 大白话解释
原子性 一个操作被拆成多步，中间被别的线程插入
可见性 一个线程改了值，其他线程看不到最新值
有序性 编译器或 CPU 为优化发生指令重排序

一句话总结：

线程安全问题的根源是多个线程同时读写共享数据，导致原子性、可见性或有序性被破坏。

5. Java 中如何解决线程安全问题？

【答】
解决线程安全问题，核心思路是：

不共享
→ 共享但不修改
→ 修改时加保护

常见手段：

手段 适合场景
局部变量 每个线程自己用自己的数据
不可变对象 创建后不修改，比如 String
synchronized 简单互斥同步
ReentrantLock 需要可中断、超时、公平锁等能力
volatile 状态标记，可见性控制
原子类 计数器、CAS 更新
并发集合 ConcurrentHashMap、BlockingQueue
ThreadLocal 每个线程保存自己的副本

【展开】 不同工具解决的问题不一样：

synchronized / Lock：保护一段临界区，保证同一时刻只有一个线程进入。
volatile：保证可见性和一定有序性，但不保证 count++ 这种复合操作原子性。
AtomicInteger：适合简单计数、累加这类原子更新。
ConcurrentHashMap：适合并发场景下的 Map 读写。
ThreadLocal：适合线程隔离，不适合多个线程共享修改。

面试表达：

解决线程安全问题不能只说加锁。
如果能避免共享，优先避免共享；必须共享时，再根据场景选择锁、原子类、并发集合或 ThreadLocal。

一句话总结：

线程安全的解决思路是先减少共享，再控制修改；不同并发工具解决的问题不同。

6. sleep、wait、join、yield 有什么区别？

【答】
这几个方法都和线程等待有关，但用途不同。

方法 属于谁 对锁的影响 主要作用
sleep Thread 不释放当前线程已持有的锁 让当前线程睡一会儿
wait Object 释放调用 wait 的那个对象锁 等别人 notify 唤醒
join Thread 本质是等待目标线程结束，不释放当前线程已持有的其他业务锁 等某个线程执行完
yield Thread 不释放锁 提示让出 CPU，不保证一定让

【展开】 sleep 示例：

Thread.sleep(1000);

意思是：

当前线程暂停 1 秒。
如果它已经拿着锁，sleep 时不会主动释放锁。

wait 示例：

synchronized (lock) {
    lock.wait();
}

意思是：

当前线程必须先拿到 lock。
调用 wait 后，会释放 lock，并进入等待。
后续需要其他线程 notify/notifyAll 唤醒。

join 示例：

thread.join();

意思是：

当前线程等待 thread 执行结束后再继续。

注意：

join 底层会用 wait 等待目标线程结束。
但面试里不要简单说“join 会释放锁”。
更准确的说法是：join 等待的是目标线程结束，不会释放当前线程已经持有的其他业务锁。

yield：

只是提示线程调度器：我愿意让出 CPU。
但调度器不一定听，所以不能用它控制业务顺序。

一句话总结：

sleep 是睡眠，不释放锁；wait 是等待通知，会释放指定对象锁；join 是等另一个线程结束；yield 只是让出 CPU 的提示。

7. wait/notify 的使用规则是什么？

【答】
wait/notify 是对象监视器上的线程通信机制，必须配合 synchronized 使用。

核心规则：

  1. 必须先拿到对象锁，才能调用这个对象的 wait/notify。
  2. wait 会释放锁。
  3. notify 只唤醒一个等待线程，notifyAll 唤醒所有等待线程。
  4. 判断条件要用 while，不要用 if。

【展开】 标准写法：

synchronized (lock) {
    while (!condition) {
        lock.wait();
    }
    // 条件满足后执行业务
}

为什么用 while？

线程被唤醒，不代表条件一定满足。
可能是虚假唤醒，也可能是别的线程先抢到锁并改变了条件。
所以醒来后要重新检查条件。

通知方：

synchronized (lock) {
    condition = true;
    lock.notifyAll();
}

为什么很多时候建议 notifyAll？

notify 只叫醒一个线程，如果叫醒的线程不是当前条件需要的线程，可能继续等。
notifyAll 会把所有等待线程叫醒，让它们重新竞争锁并检查条件，虽然成本更高，但更不容易写错。

一句话总结：

wait/notify 必须在 synchronized 里用，wait 后用 while 重新判断条件，生产中更常用 notifyAll 降低误唤醒风险。

9. ThreadLocal 是什么？为什么会有内存泄漏？

【答】
ThreadLocal 可以给每个线程保存一份自己的变量副本，线程之间互不影响。

常见用途：

保存当前登录用户
保存 traceId
保存请求上下文

【展开】

private static final ThreadLocal<String> USER_ID = new ThreadLocal<>();

USER_ID.set("1001");
String userId = USER_ID.get();
USER_ID.remove();

它不是把数据存在 ThreadLocal 对象自己里面，而是存在当前线程的 ThreadLocalMap 里。

flowchart LR T["Thread 当前线程"] --> M["ThreadLocalMap"] M --> K["key: ThreadLocal 弱引用"] M --> V["value: 用户数据"]

为什么会内存泄漏？

线程池里的线程会长期存活。
如果 ThreadLocal 用完不 remove，value 可能一直挂在线程上。
请求结束了，但数据还在线程里，后面就可能造成内存泄漏或数据串用。

正确习惯：

try {
    USER_ID.set("1001");
    // 业务代码
} finally {
    USER_ID.remove();
}

面试表达：

ThreadLocal 适合保存线程上下文，但在线程池环境下一定要 remove。
因为线程会复用，数据不清理可能造成内存泄漏，也可能让下一个请求读到上一个请求的数据。

一句话总结：

ThreadLocal 解决线程隔离，remove 解决线程复用带来的残留问题。

10. CompletableFuture 怎么做异步编排？生产上有哪些坑？

【答】
CompletableFuture 用来做异步任务编排，比如多个接口并行调用、结果合并、异常兜底。

常见方法：

方法 作用
supplyAsync 异步执行并返回结果
thenApply 对结果做转换
thenCombine 合并两个异步结果
allOf 等多个任务都完成
exceptionally 异常兜底
orTimeout 设置超时

【展开】 示例：

CompletableFuture<String> resumeFuture =
    CompletableFuture.supplyAsync(() -> queryResume(), executor);

CompletableFuture<String> interviewFuture =
    CompletableFuture.supplyAsync(() -> queryInterview(), executor);

CompletableFuture<String> result =
    resumeFuture.thenCombine(interviewFuture, (resume, interview) -> {
        return resume + interview;
    }).orTimeout(3, TimeUnit.SECONDS)
      .exceptionally(ex -> "默认结果");

生产上最容易踩的坑：

坑 说明
不传线程池 默认走 ForkJoinPool.commonPool()，阻塞 IO 多了会影响全局
不设超时 某个任务卡住，整体结果一直等
不处理异常 一个分支异常，整体可能失败
线程池太大 下游服务、数据库连接池扛不住
上下文丢失 traceId、登录用户等 ThreadLocal 信息不会自动传过去

面试表达：

CompletableFuture 适合多个互不依赖的任务并行执行。
生产使用时必须传自定义线程池，设置超时和异常兜底，同时注意上下文传递和下游限流。

一句话总结：

CompletableFuture 的重点不是会不会调用 API，而是异步之后能不能控制线程池、超时、异常和上下文。

2. 工厂模式解决什么问题？Spring 里哪里体现了工厂思想？

工厂模式把对象创建过程封装起来，让使用方不用关心具体怎么创建对象。

【展开】 不用工厂：

PayService payService = new AliPayService();

使用工厂思想：

PayService payService = payFactory.getPayService("ALI_PAY");

Spring 里的体现：

BeanFactory / ApplicationContext 本身就有工厂思想。
业务代码不用自己 new Bean，而是从 Spring 容器拿。
FactoryBean 也用于封装复杂对象创建过程。

一句话总结：

工厂模式解决对象创建复杂和调用方依赖具体实现的问题。

3. 策略模式适合什么场景？项目里怎么落地？

【答】
策略模式适合“同一个业务动作，有多种不同实现”的场景。

典型场景：

不同支付方式
不同登录方式
不同优惠券计算规则
不同文件解析方式

【展开】 不用策略模式时：

if 支付宝
else if 微信
else if 银行卡

策略模式思路：

定义统一接口。
每种策略一个实现类。
根据类型从 Map 中取对应策略执行。

看图重点：策略模式把不同处理方式拆成多个实现类，调用方只负责选择策略，不再写一堆 if/else。

Spring 项目常见落地：

@Autowired
private Map<String, PayStrategy> payStrategyMap;

一句话总结：

策略模式用多个实现类替代大量 if/else，让新增规则更容易扩展。

4. 模板方法模式是什么？Spring 里有哪些例子？

【答】
模板方法模式是：父类定义固定流程，子类实现其中可变步骤。

【展开】 可以这样理解：

流程固定：打开文件 -> 解析数据 -> 校验数据 -> 入库。
变化点：不同文件格式的解析方式不同。

Spring 中常见模板思想：

类 说明
JdbcTemplate 固定 JDBC 资源获取、执行、关闭流程
RedisTemplate 封装 Redis 操作流程
RestTemplate 封装 HTTP 调用流程

一句话总结：

模板方法把固定流程放在模板里，把变化步骤留给子类或回调实现。

5. 代理模式是什么？静态代理和动态代理有什么区别？

【答】
代理模式就是不直接访问目标对象，而是通过代理对象访问，并在调用前后增强逻辑。

Spring AOP 就大量使用代理思想。

【展开】

类型 说明
静态代理 代理类提前写好
动态代理 运行时生成代理对象

动态代理常见方式：

JDK 动态代理：基于接口。
CGLIB 动态代理：基于继承生成子类。

常见增强：

事务
日志
权限
方法耗时统计

一句话总结：

代理模式的核心是通过代理对象包一层，在不改目标方法的情况下增加通用能力。

6. 责任链模式适合什么场景？

【答】
责任链模式适合一个请求需要经过多个处理节点的场景。

典型场景：

网关过滤器
登录校验
参数校验
风控校验
审批流程
订单处理流程

【展开】 责任链思路：

请求先到第一个处理器。
处理完交给下一个处理器。
中间任何一个处理器都可以决定继续或中断。
flowchart LR A["请求"] --> B["参数校验"] B --> C["登录校验"] C --> D["权限校验"] D --> E["业务处理"]

看图重点：责任链强调“一个请求按顺序经过多个处理器”，每个处理器只负责自己的判断和处理。

Spring MVC 的过滤器、拦截器、Gateway Filter 都有责任链思想。

一句话总结：

责任链适合多步骤处理流程，让每个步骤独立，顺序可编排。

1. Spring Boot 自动装配原理是什么？

【答】
Spring Boot 自动装配就是：项目启动时，Spring Boot 根据 classpath 中已有的依赖和配置，自动帮我们创建合适的 Bean。

核心是：

加载自动配置类
→ 判断条件是否满足
→ 满足条件就创建 Bean

【展开】

flowchart LR A["启动 Spring Boot"] --> B["@EnableAutoConfiguration"] B --> C["读取自动配置类"] C --> D["@Conditional 条件判断"] D --> E["满足条件"] E --> F["注册 Bean"]

常见条件注解：

注解 大白话解释
@ConditionalOnClass classpath 里有某个类才生效
@ConditionalOnMissingBean 容器里没有这个 Bean 才创建
@ConditionalOnProperty 配置文件里开启了某个配置才生效
@ConditionalOnBean 容器里已经有某个 Bean 才生效

面试表达：

Spring Boot 不是无脑创建所有 Bean，而是先加载自动配置类，再通过各种 Conditional 条件判断当前项目是否需要这个配置。
如果用户自己定义了 Bean，很多自动配置会因为 ConditionalOnMissingBean 失效，优先使用用户自己的配置。

版本注意：

不同 Spring Boot 版本加载自动配置类的文件位置不完全一样。
老版本常见 `spring.factories`，新版本常见 `AutoConfiguration.imports`。
面试重点不是死背文件名，而是说清“加载自动配置类 + 条件判断 + 注册 Bean”这条主线。

一句话总结：

自动装配的本质是：Spring Boot 提前准备很多自动配置类，再按条件选择性生效。

2. starter 是什么？和自动配置有什么关系？

【答】
starter 可以理解成一组依赖的打包入口。

它的作用是：

帮我们把某个功能需要的依赖一次性引进来。

比如：

spring-boot-starter-web

会引入 Spring MVC、Tomcat、Jackson 等 Web 开发常用依赖。

【展开】 starter 和自动配置不是一回事：

概念 作用
starter 负责引入依赖
自动配置 负责根据依赖和条件创建 Bean

它们的关系：

starter 把依赖放进项目
→ classpath 里出现相关类
→ 自动配置类条件满足
→ Spring Boot 创建对应 Bean
flowchart LR A["引入 starter"] --> B["依赖进入 classpath"] B --> C["自动配置条件满足"] C --> D["创建对应 Bean"]

面试表达：

starter 主要解决依赖管理问题，自动配置解决 Bean 创建问题。
starter 本身不等于自动配置，但它会让自动配置具备生效条件。

一句话总结：

starter 管依赖，自动配置管 Bean，它们配合起来才让 Spring Boot 用起来简单。

3. @SpringBootApplication 由哪些注解组成？

【答】
@SpringBootApplication 是一个组合注解，主要包含：

  1. @SpringBootConfiguration
  2. @EnableAutoConfiguration
  3. @ComponentScan

【展开】

注解 作用
@SpringBootConfiguration 表示这是一个配置类
@EnableAutoConfiguration 开启自动装配
@ComponentScan 扫描当前包及子包下的组件
flowchart TB A["@SpringBootApplication"] A --> B["@SpringBootConfiguration"] A --> C["@EnableAutoConfiguration"] A --> D["@ComponentScan"]

常见坑：

启动类最好放在项目根包下。
因为 ComponentScan 默认从启动类所在包开始往下扫描。
如果启动类放错位置，Controller、Service、Mapper 可能扫描不到。

一句话总结：

@SpringBootApplication 不是魔法，它就是配置类、自动装配、组件扫描三个能力的组合。

4. Spring Boot 如何做统一异常处理？

【答】
Spring Boot Web 项目通常用 @RestControllerAdvice + @ExceptionHandler 做统一异常处理。

这样 Controller 里不用到处写 try/catch，异常可以统一返回标准 JSON。

【展开】

@RestControllerAdvice
public class GlobalExceptionHandler {

    @ExceptionHandler(BusinessException.class)
    public Result<?> handleBusinessException(BusinessException e) {
        return Result.fail(e.getMessage());
    }

    @ExceptionHandler(Exception.class)
    public Result<?> handleException(Exception e) {
        return Result.fail("系统繁忙，请稍后再试");
    }
}

常见处理方式：

异常类型 处理方式
业务异常 返回明确业务提示
参数校验异常 返回字段错误信息
未知异常 记录日志，返回统一兜底提示

面试表达：

统一异常处理的目的不是吞异常，而是统一响应格式、减少重复代码，并且保证未知异常能记录日志，方便排查。

一句话总结：

统一异常处理就是把 Controller 里分散的异常返回逻辑，集中到一个全局处理器里。

5. Spring Boot 如何实现参数校验？

【答】
Spring Boot 常用 Bean Validation 做参数校验。

一般写法是：

DTO 字段上加校验注解
Controller 参数上加 @Valid 或 @Validated
校验失败后由统一异常处理返回错误信息

【展开】

public class UserCreateRequest {

    @NotBlank(message = "用户名不能为空")
    private String username;

    @Min(value = 18, message = "年龄不能小于18")
    private Integer age;
}

Controller：

@PostMapping("/users")
public Result<?> create(@Valid @RequestBody UserCreateRequest request) {
    return Result.ok();
}

常见注解：

注解 作用
@NotNull 不能为 null
@NotBlank 字符串不能为 null 且不能为空白
@NotEmpty 集合或字符串不能为空
@Min / @Max 数值范围
@Pattern 正则校验

面试表达：

参数校验最好放在 DTO 上，不要把大量 if 判断写在 Controller 里。
校验失败后配合统一异常处理，返回统一格式的错误信息。

一句话总结：

参数校验就是用注解声明规则，再让 Spring 在进入业务方法前自动检查。

1. Spring MVC 一次请求的执行流程是什么？

【答】
Spring MVC 一次请求的核心流程是：

请求进入 DispatcherServlet
→ HandlerMapping 找到处理器
→ HandlerAdapter 调用 Controller 方法
→ 参数绑定和类型转换
→ 执行业务方法
→ 返回结果
→ HttpMessageConverter 写出 JSON

【展开】

flowchart TB A["浏览器/客户端请求"] --> B["DispatcherServlet"] B --> C["HandlerMapping 找 Controller"] C --> D["HandlerAdapter 调用方法"] D --> E["参数绑定"] E --> F["Controller 执行业务"] F --> G["返回结果"] G --> H["HttpMessageConverter 写 JSON"]

看图重点：Spring MVC 请求处理不是 Controller 自己完成的，而是 DispatcherServlet 调度多个组件协作完成。

面试表达：

DispatcherServlet 是入口，它不直接执行业务，而是协调 HandlerMapping、HandlerAdapter、参数解析器、消息转换器等组件完成请求处理。

一句话总结：

Spring MVC 的主线就是 DispatcherServlet 接请求，找到 Controller，执行方法，再把结果写回去。

2. DispatcherServlet 的作用是什么？

【答】
DispatcherServlet 是 Spring MVC 的前端控制器。

它负责接收所有匹配的 Web 请求，然后分发给具体的 Controller。

【展开】 它主要做这些事：

工作 说明
接收请求 所有符合映射的请求先到它这里
查找处理器 通过 HandlerMapping 找 Controller 方法
调用处理器 通过 HandlerAdapter 调用目标方法
处理返回值 返回 JSON、页面或其他响应
统一异常入口 异常会进入异常解析流程

可以这样理解：

DispatcherServlet 不负责具体业务，它负责调度 Spring MVC 的各个组件。

一句话总结：

DispatcherServlet 是 Spring MVC 的总入口和总调度，不是普通 Controller。

3. @RequestParam、@PathVariable、@RequestBody 有什么区别？

【答】
这三个注解都是拿请求参数的，但参数来源不同。

注解 参数来源 示例
@RequestParam 查询参数或表单参数 /users?id=1
@PathVariable URL 路径变量 /users/1
@RequestBody 请求体 JSON POST JSON

【展开】

@GetMapping("/users")
public User query(@RequestParam Long id) {
    return userService.query(id);
}
@GetMapping("/users/{id}")
public User detail(@PathVariable Long id) {
    return userService.detail(id);
}
@PostMapping("/users")
public void create(@RequestBody UserCreateRequest request) {
    userService.create(request);
}

面试表达：

GET 查询条件一般用 RequestParam，REST 风格资源 ID 常用 PathVariable，POST/PUT 提交 JSON 对象常用 RequestBody。

一句话总结：

RequestParam 拿问号后面的参数，PathVariable 拿路径里的参数，RequestBody 拿请求体里的 JSON。

4. 拦截器和过滤器有什么区别？

【答】
过滤器是 Servlet 规范里的组件，拦截器是 Spring MVC 里的组件。

它们都能拦截请求，但位置不同。

【展开】

对比点 Filter 过滤器 HandlerInterceptor 拦截器
来源 Servlet 规范 Spring MVC
执行位置 进入 Spring MVC 前 找到 Controller 前后
能否拿到 Spring Bean 可以，但需要配置 天然在 Spring 容器里
常见用途 编码、跨域、认证入口 登录校验、权限、日志、耗时统计

执行位置：

请求
→ Filter
→ DispatcherServlet
→ Interceptor
→ Controller

拦截器常见三个方法：

方法 作用
preHandle Controller 执行前
postHandle Controller 执行后，视图渲染前
afterCompletion 请求完成后

一句话总结：

Filter 更靠外，属于 Servlet；Interceptor 更靠近 Controller，属于 Spring MVC。

5. Spring MVC 如何做统一异常处理？

【答】
Spring MVC 常用 @ControllerAdvice 或 @RestControllerAdvice 配合 @ExceptionHandler 做统一异常处理。

REST 接口更常用 @RestControllerAdvice，直接返回 JSON。

【展开】

@RestControllerAdvice
public class WebExceptionHandler {

    @ExceptionHandler(MethodArgumentNotValidException.class)
    public Result<?> handleValidException(MethodArgumentNotValidException e) {
        return Result.fail("参数不合法");
    }

    @ExceptionHandler(Exception.class)
    public Result<?> handleException(Exception e) {
        return Result.fail("系统异常");
    }
}

和 Spring Boot 的关系：

Spring Boot Web 项目底层还是 Spring MVC。
所以统一异常处理的核心机制来自 Spring MVC，只是 Spring Boot 帮我们简化了配置。

一句话总结：

统一异常处理就是把 Controller 抛出的异常集中处理，保证接口返回格式一致。

1. MyBatis 中 #{} 和 ${} 有什么区别？

【答】
#{} 是预编译参数，占位符方式，安全。

${} 是字符串拼接，直接把内容拼进 SQL，有 SQL 注入风险。

【展开】

select * from user where id = #{id}

最终类似：

select * from user where id = ?

参数由数据库驱动安全设置。

而：

select * from user order by ${field}

会直接拼接字符串。

写法 本质 是否安全 常见用途
#{} 预编译占位符 安全 普通参数
${} 字符串拼接 有风险 表名、字段名、排序字段等无法预编译的位置

面试表达：

能用 #{} 就不要用 ${}。
如果必须用 ${} 拼字段名或表名，要做白名单校验，不能直接相信前端传参。

一句话总结：

#{} 是参数占位，${} 是字符串拼接；防 SQL 注入优先用 #{}。

2. MyBatis 的执行流程是什么？

【答】
MyBatis 执行 Mapper 方法的大致流程是：

调用 Mapper 接口方法
→ Mapper 代理对象接收调用
→ 找到 mappedStatement
→ Executor 执行 SQL
→ ParameterHandler 设置参数
→ StatementHandler 操作 JDBC
→ ResultSetHandler 封装结果

【展开】

flowchart TB A["Mapper 接口方法"] --> B["Mapper 代理对象"] B --> C["MappedStatement"] C --> D["Executor"] D --> E["ParameterHandler"] E --> F["StatementHandler / JDBC"] F --> G["ResultSetHandler"] G --> H["返回 Java 对象"]

看图重点：MyBatis 执行流程的主线是 Mapper 代理找到 SQL，再通过 Executor、StatementHandler、ResultSetHandler 完成执行和结果映射。

可以这样理解：

我们写的是接口，MyBatis 运行时生成代理对象。
代理对象根据方法名找到对应 SQL，然后通过 Executor 执行，最后把结果映射成 Java 对象。

一句话总结：

MyBatis 的核心是 Mapper 代理调用 SQL，再把数据库结果映射回 Java 对象。

3. MyBatis 动态 SQL 常用标签有哪些？

【答】
动态 SQL 用来根据条件灵活拼 SQL。

常见标签：

标签 作用
if 条件判断
where 自动处理 where 和多余 and
set 更新时自动处理逗号
foreach 遍历集合，常用于 in
choose/when/otherwise 类似 if/else
trim 自定义前缀、后缀处理

【展开】

<select id="listUsers" resultType="User">
  select * from user
  <where>
    <if test="name != null and name != ''">
      and name = #{name}
    </if>
    <if test="status != null">
      and status = #{status}
    </if>
  </where>
</select>

foreach 示例：

<select id="listByIds" resultType="User">
  select * from user
  where id in
  <foreach collection="ids" item="id" open="(" separator="," close=")">
    #{id}
  </foreach>
</select>

面试表达：

动态 SQL 的重点是少写字符串拼接，并避免 where 后面多 and、update 后面多逗号这类错误。

一句话总结：

动态 SQL 就是让 SQL 按条件生成，最常用的是 if、where、set、foreach。

4. MyBatis 一级缓存和二级缓存是什么？

【答】
MyBatis 有一级缓存和二级缓存。

缓存 作用范围 默认是否开启
一级缓存 同一个 SqlSession 默认开启
二级缓存 同一个 namespace 需要配置开启

【展开】 一级缓存：

同一个 SqlSession 中，执行相同 SQL 和参数，可能直接从缓存拿结果。

但只要执行增删改操作，默认就会清理当前 SqlSession 的一级缓存；commit、rollback、close 后，这个 SqlSession 的一级缓存也不会继续保留给后续请求使用。

二级缓存：

作用范围是 Mapper namespace。
多个 SqlSession 可以共享，但需要开启，并且实体通常要可序列化。

面试注意：

实际项目里 MyBatis 二级缓存用得不多。
因为它和数据一致性、事务边界、分布式部署关系复杂。
更常见的是使用 Redis 做业务缓存。

Spring 项目里还要补一句：

一级缓存虽然默认是 SqlSession 级别，但在 Spring 管理 MyBatis 时，SqlSession 通常由框架按事务边界管理。
如果不在同一个事务或同一个 SqlSession 中，多次 Mapper 调用不一定能复用一级缓存。

一句话总结：

一级缓存是 SqlSession 级别，二级缓存是 namespace 级别；Spring 项目里不要过度依赖 MyBatis 缓存，生产更常用 Redis 做业务缓存。

5. MyBatis 如何防止 SQL 注入？

【答】
核心原则是：普通参数使用 #{}，避免使用 ${} 直接拼接用户输入。

【展开】 安全写法：

select * from user where username = #{username}

危险写法：

select * from user where username = '${username}'

如果必须动态拼字段，例如排序：

order by ${sortField}

就必须做白名单：

只允许 create_time、name、id 这些后端定义好的字段。
前端传来的字段必须先校验，不能直接拼。

面试表达：

SQL 注入的根本原因是把用户输入当 SQL 结构直接执行。
MyBatis 里优先使用 #{} 走预编译。如果必须用 ${} 拼接 SQL 结构，就要做白名单限制。

一句话总结：

防 SQL 注入不是只靠 MyBatis，而是要避免直接拼用户输入；能用 #{} 就用 #{}，必须 ${} 就做白名单。

1. Spring IOC 是什么？解决了什么问题？

【答】
IOC 是控制反转。

以前对象由我们自己 new，现在对象交给 Spring 容器创建、管理和注入。

它解决的是对象创建和对象依赖管理的问题。

【展开】 没有 IOC：

UserService userService = new UserServiceImpl();

有 IOC：

@Service
public class UserService {
}

@RestController
public class UserController {
    private final UserService userService;

    public UserController(UserService userService) {
        this.userService = userService;
    }
}

可以这样理解：

我们不再到处 new 对象，而是把对象交给 Spring 容器。
需要对象时，由 Spring 帮我们注入。

IOC 和 DI 的关系：

概念 含义
IOC 控制反转，对象创建控制权交给容器
DI 依赖注入，容器把依赖对象注入进来

一句话总结：

IOC 是思想，DI 是实现方式；Spring 通过容器帮我们创建对象和装配依赖。

【答】
Spring Bean 生命周期可以按主线记：

实例化
→ 属性赋值
→ 初始化前置处理
→ 初始化
→ 初始化后置处理
→ 使用
→ 销毁

【展开】

面试重点：

阶段 说明
实例化 创建对象
属性赋值 注入依赖
Aware 回调 拿到 BeanName、ApplicationContext 等
BeanPostProcessor 初始化前后扩展点，AOP 代理常和它有关

一句话总结：

3. Spring AOP 是什么？底层怎么实现？

【答】
AOP 是面向切面编程。

它可以把日志、事务、权限、监控这类通用逻辑，从业务代码里抽出来，统一增强。

Spring AOP 底层主要通过动态代理实现。

【展开】

flowchart LR A["调用方"] --> B["代理对象"] B --> C["前置增强"] C --> D["目标方法"] D --> E["后置增强"]

常见代理方式：

方式 说明
JDK 动态代理 目标类实现接口时常用
CGLIB 代理 目标类没有接口时，通过生成子类代理

常见应用：

事务管理
接口日志
权限校验
方法耗时统计
监控埋点

面试表达：

Spring AOP 的核心是代理对象。
调用方以为自己调的是目标对象，实际先经过代理对象，代理对象在目标方法前后加增强逻辑。

一句话总结：

AOP 就是用代理把通用逻辑织入业务方法，减少重复代码。

4. Spring 事务为什么会失效？

【答】
Spring 事务失效最常见原因是：没有走到 Spring 代理对象。

常见情况：

原因 说明
方法内部自调用 同一个类里 this.xxx() 调用，没有经过代理
方法不是 public 代理事务通常要求 public 方法
异常被 catch 掉 异常没有抛出，事务不知道要回滚
抛 checked exception 默认只回滚 RuntimeException 和 Error
数据库不支持事务 比如非事务引擎
没被 Spring 管理 对象不是容器里的 Bean

【展开】 自调用例子：

public void outer() {
    this.inner();
}

@Transactional
public void inner() {
    // 数据库操作
}

问题：

outer 调 inner 是 this 调用，没有经过代理对象。
所以 inner 上的事务增强不会生效。

异常被吞：

@Transactional
public void save() {
    try {
        // 数据库操作
    } catch (Exception e) {
        // 只记录日志，不继续抛出
    }
}

问题：

异常被 catch 掉，事务拦截器认为方法正常结束，就不会回滚。

一句话总结：

Spring 事务靠代理增强，没走代理、异常没抛出、异常类型不匹配，都可能导致事务不生效。

5. Spring 如何解决循环依赖？

【答】
Spring 主要通过三级缓存解决单例 Bean 的 setter 循环依赖。

注意边界：

能解决的是单例 Bean 的属性注入循环依赖。
构造器循环依赖通常解决不了。
prototype 多例 Bean 的循环依赖也不适合靠三级缓存解决。

【展开】 三级缓存：

缓存 放什么
一级缓存 singletonObjects 完整初始化好的 Bean
二级缓存 earlySingletonObjects 提前暴露的半成品 Bean
三级缓存 singletonFactories 创建早期 Bean 引用的工厂

大致流程：

A 创建中，需要注入 B。
B 创建中，又需要注入 A。
Spring 从三级缓存拿到 A 的早期引用，先注入给 B。
B 完成后再回到 A，A 继续完成初始化。
flowchart TB A["创建 A"] --> B["A 需要 B"] B --> C["创建 B"] C --> D["B 需要 A"] D --> E["从缓存拿 A 的早期引用"] E --> F["B 完成"] F --> G["A 完成"]

看图重点：先记住三级缓存分别放什么；真正解决循环依赖时，Spring 会从三级缓存暴露早期引用，再逐步放入二级、一级缓存。

面试表达：

三级缓存不是鼓励写循环依赖。
它只是 Spring 为单例 setter 注入场景提供的兜底能力。
实际项目中出现循环依赖，通常说明设计边界不清晰，最好通过拆分职责或事件解耦消除。

版本注意：

较新的 Spring Boot 项目默认更倾向于禁止循环依赖。
所以面试回答要说清楚：三级缓存说明的是 Spring 解决部分循环依赖的机制，不代表项目里应该依赖循环引用。

一句话总结：

Spring 通过提前暴露单例 Bean 的早期引用解决部分循环依赖，但构造器循环依赖不适用。

1. 单体和微服务怎么选？服务怎么拆？（补充）

【答】
不是微服务一定比单体好。

团队小、业务简单、还在验证时，用单体或模块化单体。模块要独立发布、独立扩容，或者几个团队互相阻塞了，再按业务领域拆，不要按表或按技术层拆。

【展开】

对比 单体 微服务
开发部署 一个包，简单 多个服务，发布和联调都变重
扩容 只能整包扩 可以按服务扩
故障 一处故障影响整站 可以隔离，但调用链变长
数据 本地事务就够 跨库没有同一个本地事务
排错 一份日志 要链路和集中日志 
按业务领域拆：用户、订单、库存、支付，各管各的业务。
一个服务一个库：别的服务不要直接读写这个库。
先拆大块。团队小、没有独立发布需求，拆完就是分布式单体。
拆之前先想清楚数据怎么拆、失败了怎么补、出问题怎么查。

一句话总结：

微服务是为了独立发布和协作，不是为了显得架构高级。能用本地事务做完的，不要先拆。

2. 什么是服务雪崩？怎么防？（补充）

【答】
一个下游变慢或挂了，调用它的线程和连接池被占满，上游也跟着不能干活，故障再往更上游传，整条链垮掉。这就是雪崩。

【展开】

flowchart LR A["库存变慢"] --> B["订单服务的 Feign 线程被占满"] B --> C["订单服务自己也开始超时"] C --> D["网关和更上游被拖死"]
手段 作用
超时 不等到线程被无限占用
限流 入口先丢掉扛不住的流量
熔断 下游持续失败时，暂时不要再打
降级 非核心功能返回默认值，保主流程
隔离 不同下游用不同线程池或并发额度，一个慢的不占光所有线程

一句话总结：

雪崩是慢调用把上游线程耗尽。先把超时设上，再用限流、熔断、降级和隔离把链切断。

3. CAP 和 BASE 是什么？注册中心为什么常选 AP？（补充）

【答】
CAP 里的 P（网络分区）躲不掉，所以实际是在 C 和 A 里选。注册中心短暂不一致可以接受，不可用不行，所以默认偏 AP。业务写操作能接受晚几秒一致时，用 BASE，不要默认上全局事务。

【展开】

系统 倾向 说明
Eureka AP 自我保护，宁可留下可能失效的实例
Nacos 临时实例 AP 业务服务的默认模式
Nacos 持久实例 CP 注册信息不自动删，服务端探测
ZooKeeper CP 选主期间不可用 
调用方本地有一份实例列表。偶尔打到刚下线的实例，重试一次即可。
注册中心为了强一致而拒绝服务，所有调用方都会找不到地址，代价更大。

一句话总结：

P 必须要，注册中心选 A；业务上能最终一致就走 BASE，不要把 Seata 当默认。

1. 注册中心有什么作用？Nacos 服务注册发现流程是什么？

【答】
注册中心的作用是统一管理服务地址。

服务启动后，把自己的地址注册到 Nacos；其他服务调用它时，先从 Nacos 拿到可用实例列表，再选择一个实例发起调用。

【展开】

flowchart LR A["用户服务启动"] --> B["注册到 Nacos"] C["订单服务"] --> D["从 Nacos 拉取用户服务实例"] D --> E["选择一个实例"] E --> F["发起远程调用"]

不用注册中心时：

订单服务要把用户服务地址写死。
用户服务扩容、缩容、换机器，都要改配置。

使用注册中心后：

服务地址交给 Nacos 管。
调用方只关心服务名，不直接关心 IP 和端口。

面试表达：

Nacos 注册中心主要解决服务注册和服务发现问题。
服务提供者启动时注册实例，服务消费者根据服务名拉取实例列表，再结合负载均衡选择一个实例调用。

一句话总结：

注册中心就是微服务的服务通讯录，谁上线、谁下线、谁能调用，都由它统一维护。

2. Nacos 如何判断服务是否健康？

【答】
Nacos 会通过心跳和健康检查判断服务是否可用。

临时实例通常需要服务定期上报心跳；如果长时间没有心跳，Nacos 会把实例标记为不健康，甚至剔除。

【展开】 可以这样理解：

服务每隔一段时间告诉 Nacos：我还活着。
如果 Nacos 很久没收到消息，就认为这个实例可能挂了。
flowchart LR A["服务实例"] -->|定时心跳| B["Nacos"] B --> C{"是否按时收到心跳?"} C -->|是| D["实例健康"] C -->|否| E["标记不健康/剔除"]

为什么重要？

如果注册中心不知道某个实例挂了，调用方还可能继续把请求打到坏实例上，导致接口失败。

面试表达：

Nacos 会维护服务实例的健康状态。调用方获取实例列表时，通常只会拿到健康实例，从而减少请求打到故障节点的概率。

一句话总结：

健康检查的目的就是把坏实例及时从可调用列表里拿掉。

3. Nacos 和 Eureka 有什么区别？

【答】
Nacos 和 Eureka 都能做注册中心，但 Nacos 能力更丰富。

对比点 Nacos Eureka
注册中心 支持 支持
配置中心 支持 不支持
临时实例 支持 支持类似心跳机制
持久实例 支持 不重点支持
Spring Cloud Alibaba 常用 Spring Cloud Netflix 旧体系常见

【展开】 面试不要只说“谁好谁坏”，更稳的说法是：

Eureka 主要是注册中心。
Nacos 同时支持注册中心和配置中心，在 Spring Cloud Alibaba 技术栈中更常用。

Nacos 还支持不同一致性模型：

临时实例更偏 AP，强调可用性。
持久实例更偏 CP，强调一致性。

一句话总结：

Eureka 主要管服务发现，Nacos 既能管服务发现，也能管配置，更适合 Spring Cloud Alibaba 体系。

再补三句，避免只停在“谁功能多”：

Eureka 只有 AP。短时间大量心跳丢失时它会自我保护，不再剔除实例，宁可留下可能已经死的实例。
Nacos 临时实例走 AP，持久实例可以走 CP。
Eureka 靠客户端定时拉取，默认大约 30 秒；Nacos 可以推送变更。Eureka 2.x 已经停更。

4. Nacos 临时实例和持久实例有什么区别？（补充）

【答】
临时实例是默认：服务自己发心跳，超时就标不健康，再超时就从列表删掉，走 AP。持久实例：注册信息留着，Nacos 服务端来探测，挂了只标不健康，不自动删，走 CP。

【展开】 Nacos 1.x 临时实例常见默认值（以实际版本为准）：

阶段 默认
心跳间隔 5 秒
标成不健康 15 秒没有心跳
从列表删除 30 秒没有心跳 
spring.cloud.nacos.discovery.ephemeral=false 才是持久实例。
普通业务服务用临时实例，挂了要自动摘掉。
Nacos 2.x 用 gRPC 长连接，连接一断就能更快发现，不再只靠定时心跳。
一般业务不要为了“更一致”去改持久实例。

一句话总结：

临时实例靠心跳，挂了会删，走 AP；持久实例靠服务端探测，不自动删，走 CP。

5. 健康实例为什么会被误摘？Nacos 挂了怎么办？（补充）

【答】
一次 Full GC 把进程停住，心跳发不出去。超过 15 秒，好实例会被当成不健康，再被删掉，流量挤到剩下几台，那几台也会被打垮。

Nacos 服务端挂了是另一件事：客户端手里有一份实例列表的内存缓存，还会落一份本地文件。老实例还能调，新扩出来的实例发现不了。配置也有本地快照，但那是配置，不是实例列表，两件事分开说。

【展开】

保护阈值：健康实例占比低于阈值时，Nacos 把不健康实例也一起返回。
目的是不要把全部流量压到最后几台健康实例上。
代价是调用方可能打到坏实例，所以还要有超时、重试和熔断。
没有触发保护阈值时，列表里全是不健康实例，就应该直接失败，不要硬挑一台死的打。

一句话总结：

GC 会把好实例误摘；保护阈值是为了防止剩下的实例被压死。Nacos 挂了靠本地缓存撑住，但看不到新实例。

6. 微服务里的负载均衡是怎么做的？（补充）

【答】
这是客户端负载均衡。调用方先按服务名从 Nacos 拿到实例列表，再自己选一台。现在用 Spring Cloud LoadBalancer，默认轮询。Ribbon 已经停更。

【展开】

flowchart LR A["订单服务"] --> B["按服务名找列表"] B --> C["LoadBalancer 选一台"] C --> D["发 HTTP"]
对比 客户端负载均衡 服务端负载均衡
谁来选 调用方自己选 Nginx 这种入口选
典型 Spring Cloud LoadBalancer Nginx、网关后面的转发
结果 少一跳，调用方要自己处理列表 调用方只看到一个地址 
常见策略：轮询、随机。权重要自己做，让机器更好的实例多分一点。
同机房优先可以减少跨机房调用。
列表里没有健康实例时，这次调用失败，不要假装还能打出去。

一句话总结：

负载均衡发生在调用方：拿列表，再按策略选一台。它和 Nginx 转发不是一回事。

7. 服务发版时怎么做优雅下线？（补充）

【答】
先从 Nacos 摘掉这个实例，等别的调用方不再把新请求打过来，再停止接收新请求，等已经进来的请求做完，最后停进程。

【展开】

直接 kill -9：实例要等心跳超时才会被删，这十几秒里流量还在打正在死的进程。
正确顺序：
1. 主动向 Nacos 注销。临时实例在客户端正常关闭时会注销，但必须发生在进程被杀掉之前。
2. 留一点时间，让其他服务的列表更新。Nacos 2.x 会推送，不要假定是瞬间全网生效。
3. 打开优雅停机，不再接新请求，把在途请求做完。
4. 再退出。
滚动发布时每个实例都按这个顺序，否则会一阵一阵地打到正在关的进程上。

一句话总结：

发版先摘流量，再等在途请求结束。先杀进程，注册中心还没来得及摘，这段时间全是失败。

3.2 Nacos 配置中心

总览 Nacos 配置中心解决的是：配置不要散落在每个服务里，应该集中管理、统一修改。

序号 题型 面试题 重点
1 是什么 配置中心有什么作用？ 集中管理
2 原理 Nacos 配置动态刷新是怎么实现的？ 监听、刷新
3 场景 Nacos 如何做环境隔离？ namespace、group、dataId
4 原理 Nacos 配置变更是怎么通知客户端的？ 长轮询、gRPC

1. 配置中心有什么作用？

【答】
配置中心用来集中管理项目配置，比如数据库配置、开关配置、限流配置、业务参数等。

没有配置中心时，配置通常写在每个服务自己的配置文件里，改一次配置可能要重新打包上线。

有配置中心后，可以统一修改、统一发布。

【展开】

flowchart LR A["Nacos 配置中心"] --> B["订单服务"] A --> C["用户服务"] A --> D["库存服务"]

适合放配置中心的内容：

业务开关
限流阈值
第三方接口地址
日志级别
部分可动态调整的业务参数

不建议随便放：

高度敏感的密钥明文
频繁变化到像业务数据一样的内容

一句话总结：

配置中心就是把分散在各个服务里的配置集中管起来，方便修改、发布和回滚。

2. Nacos 配置动态刷新是怎么实现的？

【答】
Nacos 客户端会监听配置变化。

当配置中心的配置发生变化后，客户端能收到变更通知，并刷新本地配置。

【展开】

flowchart LR A["修改 Nacos 配置"] --> B["发布配置"] B --> C["客户端监听到变化"] C --> D["刷新本地配置"] D --> E["业务读取新值"]

常见用法：

@RefreshScope
@RestController
public class ConfigController {

    @Value("${demo.name}")
    private String name;
}

面试注意：

不是所有配置都适合动态刷新。
像数据库连接池核心参数、线程池核心参数这类配置，即使值刷新了，也不一定代表底层对象会自动重建。
生产中要明确哪些配置支持动态变更。

一句话总结：

动态刷新不是重启应用，而是客户端监听配置变化后，把支持刷新的配置更新到应用里。

3. Nacos 如何做环境隔离？

【答】
Nacos 常用 namespace、group、dataId 做配置隔离。

概念 大白话解释
namespace 隔离环境，比如 dev、test、prod
group 隔离项目或业务组
dataId 具体配置文件名

【展开】 常见设计：

namespace：开发环境 / 测试环境 / 生产环境
group：项目名或业务线
dataId：服务名.yaml

例子：

namespace = prod
group = interview-system
dataId = resume-service.yaml

面试表达：

环境隔离的关键是不要让测试配置污染生产配置。通常用 namespace 隔离不同环境，用 group 区分项目或业务线，用 dataId 定位具体服务配置。

一句话总结：

namespace 管环境，group 管分组，dataId 管具体配置文件。

4. Nacos 配置变更是怎么通知客户端的？（补充）

【答】
客户端先在本地留一份配置，再监听变化，不是每隔一秒去问一遍。

Nacos 1.x 用长轮询：请求先被挂起，大约 30 秒内配置变了就马上返回变更的 dataId，客户端再去拉新值。一直没变，就空返回，客户端重新挂上。Nacos 2.x 改成 gRPC 长连接，服务端直接推通知，客户端收到后再拉。

【展开】

方式 问题
短轮询 大量无效请求，还有延迟
长轮询 有变化才返回，请求少
长连接 服务端能推，要维持连接 
本地快照的用途：配置中心暂时连不上，启动时还能读上次的配置。
监听到新值和“连接池、线程池会跟着重建”不是一回事。数据库连接、线程池这种对象，值变了也不会自动拆掉重建。
密钥不要明文放进 Nacos。配置要能回滚到上一版。

一句话总结：

配置刷新是本地缓存加监听：1.x 长轮询，2.x 长连接推送。不是所有配置刷新了就真的生效。

3.3 OpenFeign 远程调用

总览 OpenFeign 解决的是：服务之间调用不要手写 HTTP 细节，像调本地接口一样调远程服务。

序号 题型 面试题 重点
1 是什么 OpenFeign 是什么？调用流程是什么？ 声明式 HTTP
2 场景 OpenFeign 超时和重试怎么配置？ 超时、重试风险
3 场景 OpenFeign 调用失败怎么兜底？ fallback、Sentinel
4 场景 Feign 超时为什么要沿调用链收紧？重试有什么风险？ 超时预算、重试风暴

动画辅助：动画/07-微服务.html →「03 OpenFeign底层」

1. OpenFeign 是什么？调用流程是什么？

【答】
OpenFeign 是声明式 HTTP 客户端。

我们只需要定义接口和注解，Feign 会帮我们生成代理对象，发起远程 HTTP 调用。

【展开】

@FeignClient(name = "user-service")
public interface UserClient {

    @GetMapping("/users/{id}")
    UserDTO getById(@PathVariable Long id);
}

调用流程：

flowchart LR A["订单服务调用 UserClient"] --> B["Feign 代理对象"] B --> C["根据服务名找实例"] C --> D["负载均衡选择实例"] D --> E["发送 HTTP 请求"] E --> F["用户服务返回结果"]

面试表达：

Feign 本质还是 HTTP 调用，只是通过接口代理封装了请求构造、服务发现、负载均衡和结果转换。

一句话总结：

OpenFeign 让远程 HTTP 调用写起来像调用本地接口，但底层仍然是网络请求。

2. OpenFeign 超时和重试怎么配置？

【答】
Feign 调用必须设置合理的连接超时和读取超时。

否则下游服务变慢时，上游线程会一直等待，可能拖垮整个服务。

【展开】 常见超时：

类型 含义
连接超时 建立连接最多等多久
读取超时 请求发出后等响应最多等多久

面试表达：

Feign 超时不能拍脑袋设置，要结合接口 SLA、下游性能和业务容忍度。
超时时间太短会误杀正常请求，太长会导致线程堆积。

重试要谨慎：

查询接口可以适当重试。
下单、扣库存、支付这类非幂等接口不能随便重试，否则可能造成重复操作。

一句话总结：

Feign 一定要有超时；重试只能用在幂等场景，不能无脑开。

3. OpenFeign 调用失败怎么兜底？

【答】
OpenFeign 调用失败时，可以结合 Sentinel 做熔断降级，也可以配置 fallback 返回兜底结果。

【展开】 兜底思路：

远程调用失败
→ 不让异常无限向上传播
→ 返回默认结果或友好提示
→ 记录日志和监控

例子：

@FeignClient(name = "user-service", fallback = UserClientFallback.class)
public interface UserClient {
    @GetMapping("/users/{id}")
    UserDTO getById(@PathVariable Long id);
}

兜底不是万能的：

用户昵称查询失败，可以返回默认昵称。
扣库存失败，不能假装成功，必须明确失败或进入补偿流程。

一句话总结：

Feign 失败兜底要看业务，能降级的返回默认值，不能降级的要失败得明确。

4. Feign 超时为什么要沿调用链收紧？重试有什么风险？（补充）

【答】
超时要越往下游越短：网关长于本服务，本服务长于 Feign，Feign 长于数据库。下游先超时返回，上游才有时间做熔断和降级。反过来的话，上游先断了，下游还在空跑。

【展开】

一组能讲的数，不是标准答案，是为了说明谁比谁短：
网关 3 秒，订单服务 2 秒，Feign 读超时 1 秒，数据库 500 毫秒。
连接超时要短，比如几百毫秒，连不上就快点失败。
读超时看这个接口的 SLA，太短会误杀，太长会把线程堆死。

Spring Cloud OpenFeign 默认不重试。一旦打开：
查询可以重试；下单、扣库存、支付不能靠重试补救，除非下游有幂等。
一次用户请求如果每层都重试 2 次，打到最下游可能变成好几倍流量。这就是重试风暴。
连接池也有上限。下游变慢时，占满的是连接和线程，不只是 QPS。

一句话总结：

超时沿链路往下收。重试只给幂等接口，而且会把下游流量乘上去。

3.4 Gateway 网关

总览 Gateway 解决的是：外部请求不要直接打到各个微服务，而是先经过统一入口。

序号 题型 面试题 重点
1 是什么 Gateway 网关有什么作用？ 统一入口
2 原理 Gateway 的路由、断言、过滤器是什么？ route、predicate、filter
3 场景 网关一般做哪些事情？ 鉴权、限流、跨域、日志
4 原理 Gateway 为什么性能好？和 Nginx 有什么区别？ WebFlux、不要阻塞
5 场景 网关统一鉴权是怎么实现的？ 本地验签、防伪造

动画辅助：动画/07-微服务.html →「04 Gateway执行过程」

1. Gateway 网关有什么作用？

【答】
Gateway 是微服务系统的统一流量入口。

它可以把外部请求转发到不同后端服务，并统一处理鉴权、限流、跨域、日志等通用逻辑。

【展开】

flowchart LR A["客户端"] --> B["Gateway"] B --> C["用户服务"] B --> D["订单服务"] B --> E["库存服务"]

没有网关时：

客户端要知道每个服务的地址。
每个服务都要重复做鉴权、跨域、限流。

有网关后：

客户端只访问网关。
通用能力在网关统一处理。
后端服务专注业务。

一句话总结：

网关就是微服务系统的大门，负责统一入口和通用流量治理。

2. Gateway 的路由、断言、过滤器是什么？

【答】
Gateway 三个核心概念：

概念 作用
Route 路由 决定请求转发到哪里
Predicate 断言 判断请求是否匹配这个路由
Filter 过滤器 在请求前后做增强处理

【展开】 可以这样理解：

断言：这个请求是否符合条件？
路由：符合条件后转发到哪个服务？
过滤器：转发前后要不要做点额外处理？

例子：

Path=/api/user/**
→ 匹配用户相关请求
→ 转发到 user-service
→ 转发前检查 token

请求流程：

flowchart LR A["请求进入网关"] --> B["Predicate 判断是否匹配"] B --> C["Filter 前置处理"] C --> D["Route 转发到目标服务"] D --> E["Filter 后置处理"] E --> F["返回响应"]

一句话总结：

断言管匹配，路由管转发，过滤器管增强。

3. 网关一般做哪些事情？

【答】
网关常做这些通用能力：

统一鉴权
接口限流
跨域处理
请求日志
灰度路由
请求头透传

【展开】

能力 说明
鉴权 校验 token、判断用户身份
限流 防止突发流量打垮后端
跨域 统一处理浏览器跨域请求
日志 记录请求路径、耗时、状态码
灰度 按用户、版本、比例转发到不同服务

面试注意：

网关适合做通用逻辑，不适合写复杂业务逻辑。
业务规则应该放在具体业务服务里。

一句话总结：

网关做公共入口治理，不应该变成大而全的业务服务。

4. Gateway 为什么性能好？和 Nginx 有什么区别？（补充）

【答】
Spring Cloud Gateway 跑在 WebFlux 和 Netty 上，少量线程扛很多连接。Zuul 1 是一个请求占一个 Servlet 线程，线程容易被占满。Gateway 和 Nginx 一起用：Nginx 在最外面做 TLS 和转发，Gateway 做鉴权、限流、按服务名转发。

【展开】

对比 Nginx Gateway
位置 最外层入口 微服务业务入口
擅长 TLS、静态资源、反向代理 鉴权、限流、灰度、服务发现
怎么扩展 配置或 Lua Java 过滤器 
Gateway 的事件循环线程很少。过滤器里不要同步查库，也不要发一个会堵很久的 HTTP。
一堵，所有请求都堵。要查就用响应式客户端，或者把鉴权做成本地校验 JWT。

一句话总结：

Gateway 靠非阻塞模型。Nginx 管入口转发，Gateway 管和业务有关的流量治理，过滤器里不能堵。

5. 网关统一鉴权是怎么实现的？（补充）

【答】
写一个全局过滤器。登录、注册放行；其他请求取出 token，在网关本地验签名和是否过期，不要每次再调用户服务。失败返回 401。成功先删掉客户端自己带的用户头，再写入解析出来的用户 id，转给下游。

【展开】

白名单：登录、注册本来就没有 token。
先删后写用户头：防止调用方伪造 X-User-Id。
下游只信任网关传下来的用户信息，不要再各写一遍 JWT 解析。
业务服务不能被外网绕过网关直接打到，否则这层鉴权等于没有。
JWT 是本地验签，网关被打满时也不会再去把用户服务打挂。

一句话总结：

网关鉴权是白名单加本地验签，再透传用户信息。要防伪造头，也要防绕过网关。

1. 限流、熔断、降级有什么区别？

【答】
三者都是服务保护手段，但解决的问题不同。

概念 解决什么问题 大白话
限流 流量太大 人太多，先排队或拒绝
熔断 下游持续失败 下游坏了，先别再打它
降级 保核心功能 非核心功能先简化或关闭

【展开】 例子：

秒杀接口 QPS 太高：限流。
库存服务连续超时：熔断。
推荐服务不可用：降级返回默认推荐。

一句话总结：

限流挡流量，熔断挡故障，降级保核心。

2. Sentinel 常见规则有哪些？

【答】
Sentinel 常见规则包括：

规则 作用
流控规则 控制 QPS 或并发线程数
熔断规则 慢调用、异常比例、异常数触发熔断
热点规则 对热点参数单独限流
系统规则 根据系统负载整体保护
授权规则 黑白名单访问控制

【展开】 最常见的是流控和熔断。

流控：请求太多时，直接拒绝一部分。
熔断：下游服务持续慢或持续报错时，暂时不再调用。

面试表达：

Sentinel 不是只做限流，它还可以做熔断降级、热点参数限流和系统保护。
实际项目中要结合接口重要程度和下游承载能力配置规则。

一句话总结：

Sentinel 的核心是给资源加保护规则，防止流量或故障把系统打垮。

3. Sentinel 如何保护 OpenFeign 调用？

【答】
OpenFeign 调用下游服务时，可以结合 Sentinel 做熔断降级。

当下游服务超时、异常或被限流时，进入 fallback，返回兜底结果。

【展开】

flowchart LR A["订单服务"] --> B["Feign 调用户服务"] B --> C{"调用是否正常?"} C -->|正常| D["返回真实结果"] C -->|异常/熔断/限流| E["进入 fallback"]

fallback 要注意：

能返回默认值的场景，可以降级。
强一致业务不能假装成功，要返回失败或进入补偿。

blockHandler 和 fallback 区别：

机制 常见含义
blockHandler 处理 Sentinel 限流、熔断这类规则拦截
fallback 处理业务异常或远程调用异常

一句话总结：

Sentinel 保护 Feign 的关键是：下游异常时快速失败或返回兜底，避免上游线程被拖死。

4. 熔断器的三种状态是什么？（补充）

【答】
关闭、打开、半开。

【展开】

flowchart LR A["关闭：正常调用，同时统计"] -->|"慢调用或异常达到阈值"| B["打开：直接拒绝"] B -->|"熔断时间到了"| C["半开：放少量请求试探"] C -->|"成功"| A C -->|"失败"| B
Sentinel 可以用慢调用比例、异常比例、异常数来打开熔断。
请求太少时不要熔断，避免偶然一次失败就断掉。
没有半开，就只能等人手工恢复，或者永远不再调用。

一句话总结：

关闭是正常统计，打开是快速失败，半开是自动试探能不能恢复。

5. 常见限流算法有哪些？Sentinel 用的是哪种？（补充）

【答】
固定窗口、滑动窗口、漏桶、令牌桶。Sentinel 统计 QPS 用滑动窗口。流控效果里，快速失败是默认；Warm Up 像令牌桶的预热；匀速排队像漏桶。

【展开】

算法 特点
固定窗口 简单。窗口交界的一瞬间可能放过将近两倍流量
滑动窗口 把一秒拆成小格，统计更平滑
漏桶 按固定速度放行，不让突发
令牌桶 按速度发令牌，允许短时突发 
下游变慢时，不要只看 QPS。
QPS 没超，但每个请求都卡着不返回，线程一样会被占光。
这时用并发线程数限流，比只卡 QPS 有用。
热点参数、系统负载是另外两条规则，不是同一种限流。

一句话总结：

滑动窗口用来统计，漏桶抹平速度，令牌桶允许一点突发。慢调用要限线程数，不要只限 QPS。

6. Sentinel 规则怎么持久化？和 Hystrix 有什么区别？（补充）

【答】
控制台里配的规则默认在应用内存里，重启就没了。生产要把规则推到 Nacos，客户端监听 Nacos，变更马上生效，重启也不丢。

【展开】

对比 Sentinel Hystrix
状态 还在维护 已经停更
隔离 并发线程数，开销小 主要靠线程池隔离，线程开销大
能力 流控、熔断、热点、系统保护，规则能动态改 主要是熔断降级 
官方控制台默认不会把规则写回 Nacos。
要么改控制台，让它推到 Nacos；要么直接在 Nacos 里维护规则，客户端来监听。
只在页面上点保存，机器一重启保护就消失。

一句话总结：

规则要放进 Nacos，不能只放在控制台内存里。Hystrix 知道它停更了就行，不要当成现在的方案。

3.6 Seata 分布式事务

总览 Seata 解决的是：一次业务操作跨多个服务、多个数据库时，数据怎么尽量保持一致。

序号 题型 面试题 重点
1 是什么 为什么需要分布式事务？ 跨服务一致性
2 原理 Seata AT 模式核心流程是什么？ TC、TM、RM、undo_log
3 场景 Seata 和最终一致性方案怎么选？ 强一致、最终一致
4 对比 2PC、TCC、Saga 分别是什么？TCC 有哪些坑？ 空回滚、悬挂、幂等
5 原理 Seata AT 的全局锁和隔离级别怎么理解？ undo_log、脏写
6 场景 本地消息表怎么做？为什么默认不用 Seata？ 最终一致

动画辅助：动画/07-微服务.html →「07 分布式事务AT与XA」

1. 为什么需要分布式事务？

【答】
单体项目里，一个业务操作通常只操作一个数据库，可以用本地事务。

微服务里，一个业务操作可能跨多个服务、多个数据库，本地事务管不了其他服务的数据，所以需要分布式事务或最终一致性方案。

【展开】 例子：下单流程。

订单服务：创建订单
库存服务：扣减库存
账户服务：扣减余额

如果订单创建成功，但库存扣减失败，就会出现数据不一致。

flowchart LR A["创建订单成功"] --> B["扣库存失败"] B --> C["数据不一致"]

面试表达：

分布式事务的核心问题是：一个业务动作拆到多个服务和多个数据库后，如何保证这些操作要么都成功，要么失败后能回滚或补偿。

一句话总结：

分布式事务解决的是跨服务、跨数据库的一致性问题。

2. Seata AT 模式核心流程是什么？

【答】
Seata AT 模式里有三个角色：

角色 作用
TC 事务协调者，负责全局事务提交或回滚
TM 事务管理者，负责开启、提交、回滚全局事务
RM 资源管理者，负责本地分支事务

AT 模式会在业务数据修改前后记录 undo_log，如果全局事务失败，可以根据 undo_log 回滚。 同时 Seata 会通过全局锁协调分支事务，尽量避免多个全局事务同时修改同一条关键数据造成脏写。

【展开】

flowchart TB A["TM 开启全局事务"] --> B["RM 执行业务 SQL"] B --> C["记录 undo_log"] C --> D["本地事务提交"] D --> E{"全局事务结果"} E -->|成功| F["TC 通知全局提交"] E -->|失败| G["TC 通知全局回滚"] G --> H["RM 根据 undo_log 回滚"]

可以这样理解：

Seata AT 模式不是一直锁着所有数据库不提交。
它会先提交本地事务，提高性能。
如果后面全局失败，再根据 undo_log 做反向补偿回滚。

面试注意：

AT 模式对数据库表有要求，通常需要 undo_log 表。
同时要注意全局事务边界不要太大，避免锁持有时间长、影响性能。
如果热点数据频繁参与全局事务，全局锁竞争会比较明显，需要结合业务拆分或改用最终一致性方案。

一句话总结：

Seata AT 模式靠 TC 协调全局事务，靠 undo_log 支持失败回滚。

3. Seata 和最终一致性方案怎么选？

【答】
不是所有分布式一致性问题都必须用 Seata。

要根据业务对一致性的要求来选。

方案 适合场景
Seata AT 业务希望像本地事务一样回滚，改造成本可接受
MQ 最终一致性 允许短暂不一致，后续可靠消息补偿
TCC 需要明确 try、confirm、cancel，业务控制更强
本地消息表 对可靠性要求高，可接受异步补偿

【展开】 下单扣库存：

如果要求强一致，可以考虑 Seata 或 TCC。
如果允许短暂不一致，可以用 MQ 最终一致性。

面试表达：

分布式事务没有银弹。强一致通常成本更高，最终一致更适合高并发场景。
实际选型要看业务能不能接受短暂不一致、失败后是否能补偿、接口是否幂等。

一句话总结：

能最终一致就别强行全局事务；必须强一致时再考虑 Seata、TCC 这类方案。

4. 2PC、TCC、Saga 分别是什么？TCC 有哪些坑？（补充）

【答】
2PC 是先问所有参与者能不能提交，都能就一起提交，有一个不能就一起回滚。TCC 是业务自己写 Try、Confirm、Cancel。Saga 是每一步都有补偿，失败了按反方向补偿。

【展开】

2PC 的问题：协调者是单点，参与者的锁要握到第二阶段，慢。
TCC 扣库存的例子：
Try 冻结 1 件。Confirm 真正扣掉。Cancel 把冻结还回去。

TCC 必须处理三件事：
空回滚：Try 没执行到，Cancel 先到了。没有 Try 记录就直接成功返回，不要去减一笔不存在的冻结。
悬挂：Cancel 已经处理完，迟到的 Try 又来了。Try 看到已经 Cancel 过，就拒绝再冻结。
幂等：Confirm 和 Cancel 都会被重复调用。用全局事务号加分支号记状态，处理过就直接返回。

Saga 没有隔离，中间状态别人看得见。流程长、可以最终一致时才用。

一句话总结：

2PC 锁得久，TCC 要自己处理空回滚、悬挂和幂等，Saga 靠补偿，适合长流程。

5. Seata AT 的全局锁和隔离级别怎么理解？（补充）

【答】
一阶段就提交本地事务，同时记下修改前、修改后的镜像，写进 undo_log。全局成功就删掉 undo_log。全局失败就按前镜像生成反向 SQL 回滚。

本地行锁在一阶段提交后已经放了。TC 再拿一把全局锁，直到整个全局事务结束，防止别人改了同一行，回滚时把别人的更新盖掉。

【展开】

默认隔离接近读未提交：一阶段已经提交，别的普通查询能读到全局事务还可能回滚的数据。
要读已提交，得在全局事务里用 select for update，让它去抢全局锁。
回滚时发现这行已经不是后镜像，说明被别人改过，自动回滚对不上，只能告警后人工处理。
热点库存、余额不要放进 AT。全局锁会跨一次甚至多次远程调用，并发会变成排队。
全局事务里不要包慢调用，锁握多久，吞吐就差多少。

一句话总结：

AT 用 undo_log 做反向回滚，用全局锁防止脏写。它默认能读到未最终确认的数据，热点行不要用。

6. 本地消息表怎么做？为什么默认不用 Seata？（补充）

【答】
两个库不在一个本地事务里。Seata 为了让它们一起成、一起败，会把全局锁握到所有分支都结束。大多数下单、扣库存、发券，接受不了这个代价，也接受得了晚几秒一致。所以默认用本地消息表，不用 Seata。

【展开】

订单服务，同一个本地事务里：
插入订单。
插入一条待发送的扣库存消息。
提交。这样不会出现订单成功、消息丢了。

提交之后再把消息发给 MQ，发送成功就改成已发送。
库存服务按订单号做唯一键：第一次扣减，重复消息直接当成功。
失败就重试。一直失败就进死信，人来看。

这几秒库存还没扣上，就是最终一致。
只有必须同一时刻一起成败、而且并发不高的操作，比如一部分资金处理，才用 TCC 或 Seata。
用的时候也不要把热点行和慢调用包进去。

一句话总结：

默认最终一致：本地事务写出业务和消息，消费端按业务单号幂等。Seata 的全局锁不适合当默认方案。

3.7 XXL-JOB 分布式定时任务

总览 XXL-JOB 解决的是：单机定时任务在多实例部署后不好管理、容易重复执行、不方便监控的问题。

序号 题型 面试题 重点
1 是什么 XXL-JOB 是什么？解决了什么问题？ 调度中心、执行器
2 原理 XXL-JOB 的执行流程是什么？ 调度、路由、执行、回调
3 场景 XXL-JOB 分片任务和失败重试怎么用？ 分片广播、幂等
4 场景 多个执行器时怎么避免任务重复执行？阻塞策略是什么？ 路由、串行、丢弃
5 对比 XXL-JOB 和 @Scheduled、Quartz 有什么区别？ 多实例会跑多次

1. XXL-JOB 是什么？解决了什么问题？

【答】
XXL-JOB 是分布式任务调度平台。

它把“什么时候执行任务”交给调度中心，把“具体执行什么任务”交给业务服务里的执行器。

【展开】 单机定时任务的问题：

服务部署多个实例后，定时任务可能重复执行。
任务执行情况不方便统一查看。
失败重试、报警、分片处理都要自己做。

XXL-JOB 的角色：

角色 作用
调度中心 管理任务、触发任务、查看日志
执行器 注册到调度中心，真正执行业务任务
任务 Handler 业务代码里的具体任务方法

一句话总结：

XXL-JOB 把任务调度和任务执行拆开，让分布式定时任务可管理、可监控、可重试。

2. XXL-JOB 的执行流程是什么？

【答】
XXL-JOB 执行流程是：

执行器启动并注册到调度中心
→ 调度中心按 cron 触发任务
→ 根据路由策略选择执行器
→ 执行器执行任务 Handler
→ 执行结果回调给调度中心

【展开】

flowchart LR A["执行器注册"] --> B["调度中心"] B --> C["按 cron 触发"] C --> D["选择执行器"] D --> E["执行任务 Handler"] E --> F["回调执行结果"]

常见路由策略：

第一个
轮询
随机
分片广播
故障转移

一句话总结：

XXL-JOB 的核心流程是调度中心触发，执行器执行，结果再回传调度中心。

3. XXL-JOB 分片任务和失败重试怎么用？

【答】
分片任务适合大批量数据处理。

调度中心把同一个任务广播给多个执行器，每个执行器拿到自己的分片编号，只处理其中一部分数据。

【展开】 例子：

一共有 4 个执行器。
分片 0 处理 id % 4 = 0 的数据。
分片 1 处理 id % 4 = 1 的数据。
分片 2 处理 id % 4 = 2 的数据。
分片 3 处理 id % 4 = 3 的数据。

失败重试注意：

定时任务必须做幂等。
因为任务可能失败重试，也可能被人工重新触发。
比如发送优惠券、结算账单、同步数据，都要防止重复处理。

一句话总结：

XXL-JOB 分片适合批量任务并行处理，失败重试必须配合幂等设计。

4. 多个执行器时怎么避免任务重复执行？阻塞策略是什么？（补充）

【答】
同一个任务不会自动在每台机器上各跑一遍。调度中心按路由选一台执行器。只有分片广播才会让多台一起跑，而且每台只处理自己的那一片。

【展开】

点 怎么处理
路由 第一台、最后一台、轮询、随机、故障转移。选中的那台才执行
分片广播 每台都收到任务，但只处理 shardIndex 对应的数据
单机串行 上次没跑完，这次排队
丢弃后续 上次没跑完，这次直接丢掉
覆盖之前 想办法停掉上次，跑这次 
调度中心错过了触发时间，要看 misfire 怎么补。
不管选哪种阻塞策略，任务本身都要幂等。
人工点一次重跑、失败重试，都可能再执行。

一句话总结：

多台执行器不是多台都跑同一份任务。路由决定跑哪台，阻塞策略决定上次没完这次怎么办，业务必须幂等。

5. XXL-JOB 和 @Scheduled、Quartz 有什么区别？（补充）

【答】
@Scheduled 写在应用里。服务有几个实例，就会跑几次，没有统一的调度和失败记录。Quartz 能做，集群要靠数据库锁，运维和页面都要自己补。XXL-JOB 把调度中心和执行器分开，有路由、分片、日志和失败重试。

【展开】

单机、不在乎错过一次，可以用 @Scheduled。
多实例还在用 @Scheduled，第一件事就是任务会重复执行。
要页面上看日志、手动触发、分片、失败告警，用 XXL-JOB 这种调度中心。

一句话总结：

@Scheduled 会在每个实例上跑。多实例要用调度中心选一台，或者分片后各跑各的。

1. Elasticsearch 是什么？为什么适合搜索？

【答】
Elasticsearch 是分布式搜索和分析引擎，适合全文检索、复杂筛选和日志检索。

它适合搜索的核心原因是使用倒排索引。

【展开】 正向索引像这样：

文档 -> 包含哪些词

倒排索引像这样：

词 -> 出现在哪些文档

例子：

“Java” -> 文档1、文档3、文档8
“Redis” -> 文档2、文档3
flowchart LR subgraph fwd["正向索引"] D1["文档1"] --> W1["Java, 面试"] D2["文档2"] --> W2["Redis, 缓存"] end subgraph inv["倒排索引"] T1["词: Java"] --> Docs1["文档1, 文档3"] T2["词: Redis"] --> Docs2["文档2, 文档3"] end

一句话总结：

ES 适合搜索，是因为倒排索引能快速从关键词找到相关文档。

2. MySQL 和 ES 如何同步数据？

【答】
MySQL 通常作为核心业务数据源，ES 作为搜索索引。

常见同步方式：

业务代码双写
MQ 异步同步
监听 MySQL binlog 同步

【展开】

方案 优点 问题
业务双写 实现简单 容易出现一边成功一边失败
MQ 异步同步 解耦，削峰 有延迟，需要处理重复消费
Binlog 同步 对业务侵入小 链路更复杂，需要维护同步组件

面试表达：

MySQL 到 ES 一般追求最终一致。
核心交易数据以 MySQL 为准，ES 主要服务搜索场景。
如果 ES 数据延迟或失败，要有重试、补偿和重建索引机制。

一句话总结：

MySQL 管准确数据，ES 管搜索查询；同步通常用 MQ 或 Binlog 做最终一致。

3. ES 深分页为什么慢？怎么优化？

【答】
ES 深分页慢，是因为 from + size 越大，每个分片要取的数据越多，最后还要在协调节点合并排序。

【展开】 例子：

from=100000, size=20

意味着 ES 不是只拿 20 条，而是要先拿到前面很多数据，再丢弃前面的，只返回最后 20 条。

flowchart TB Q["from=100000, size=20"] --> S1["分片1 取前 100020"] Q --> S2["分片2 取前 100020"] Q --> S3["分片3 取前 100020"] S1 --> M["协调节点合并排序"] S2 --> M S3 --> M M --> R["丢掉前面大量结果，只回 20 条"]

优化方式：

方案 说明
限制深翻页 产品层面限制只能翻前 N 页
search_after 基于上一页最后一条排序值继续查
scroll 适合后台批量导出，不适合用户实时翻页
优化排序字段 使用稳定、可排序的字段，比如时间 + id

一句话总结：

ES 深分页慢是因为跨分片取数和合并成本高，用户翻页用 search_after，批量导出用 scroll。

4. ES 的 text 和 keyword 有什么区别？中文分词怎么做？（补充）

【答】
text 会分词，用来做全文搜索。keyword 不分词，整段当成一个词，用来做精确匹配、过滤、聚合和排序。

【展开】

商品标题要能搜“手机”，用 text。
订单状态、用户 id、标签要精确过滤，用 keyword。
一个字段常常两个都要：text 负责搜，keyword 子字段负责聚合和排序。
中文用 IK。建索引可以用 ik_max_word，切得细；查询可以用 ik_smart，切得粗。两边差太远，会搜不到。
不要把 ES 当业务库。订单的准数仍在 MySQL，ES 只是查询模型。

一句话总结：

text 用来搜，keyword 用来精确匹配和聚合。中文搜索要指定分词器，而且索引和查询的切法要配得上。

5. ES 写入后为什么不是马上能搜到？（补充）

【答】
写入先到内存缓冲区和 translog，要 refresh 之后才变成可搜索的段。默认大约 1 秒 refresh 一次，所以 ES 是近实时，不是写完立刻能搜。

【展开】

想马上在测试里搜到，可以手动 refresh，生产不要每写一条就 refresh，成本很高。
进程挂了，内存里还没刷盘的数据靠 translog 恢复。
translog 落盘策略决定丢数据的窗口，和“能不能马上搜到”不是同一个问题。
从 MySQL 同步过来时，还会再加一层延迟：binlog 或消息本身就不是瞬时的。

一句话总结：

写进 ES 不等于已经可搜。默认要等一次 refresh，业务上把它当成近实时。

6. ES 的分片和副本是什么？（补充）

【答】
分片把一个索引拆到多台机器上。主分片数在索引建好后不要随便改。副本是主分片的拷贝，用来扛读、也用来在节点挂了之后顶上。

【展开】

分片不是越多越快。每个分片都有成本，数据量不大时，分片过多，查询要合并的结果也多。
副本数至少 1，单节点集群上副本会一直分不出去，显示黄，这是正常的。
改副本数可以在线做。主分片数要在创建时想好。
深度分页会到每个分片上取“from + size”条再合并，所以越翻越慢。

一句话总结：

主分片决定数据怎么拆开，副本决定挂了一台还能不能读。分片数按数据量定，不是越大越好。

1. Redis 常用数据类型有哪些？分别适合什么场景？

【答】
Redis 常用数据类型有 String、Hash、List、Set、ZSet。

面试不要只说名字，要能说出适合什么业务。

【展开】

类型 大白话理解 常见场景
String 普通 key-value 缓存对象 JSON、计数器、验证码
Hash 一个 key 下面多个字段 用户信息、商品信息

排行榜：ZSet，key=rank，score=分数，member=用户ID。

面试表达：

简单值用 String，对象字段用 Hash，去重用 Set，排序排行用 ZSet。

一句话总结：

2. Redis 为什么这么快？

【答】
Redis 快主要有几个原因：

  1. 数据主要在内存中操作。
  2. 使用高效的数据结构。
  3. 网络 IO 使用 IO 多路复用。
  4. 命令执行模型简单，避免大量线程切换和锁竞争。

【展开】

flowchart LR A["Redis 快"] --> B["内存操作"] A --> C["高效数据结构"] A --> D["IO 多路复用"] A --> E["单线程执行命令，减少锁竞争"]

面试注意：

Redis 单线程通常指命令执行主流程主要是单线程。
不是整个 Redis 进程只有一个线程。
新版本 Redis 在网络 IO、持久化等方面也会使用额外线程。

为什么单线程还快？

因为 Redis 操作大多是内存操作，真正瓶颈往往不是 CPU。
单线程避免了多线程锁竞争和上下文切换，再配合 IO 多路复用，可以支撑很高并发。

一句话总结：

Redis 快不是只因为单线程，而是内存操作、高效结构、IO 多路复用和简单执行模型共同作用。

动画辅助：动画/08-Redis.html → 专题「05 内存机制」

1. RDB 和 AOF 有什么区别？

【答】
RDB 是快照，AOF 是操作日志。

对比点 RDB AOF
本质 某一时刻的数据快照 写命令追加日志
恢复速度 通常较快 通常较慢
数据安全 可能丢失最近一段数据 丢失更少，取决于刷盘策略
文件大小 通常较小 可能较大，需要重写
适合场景 备份、快速恢复 更高数据安全要求

【展开】 可以这样理解：

RDB 像拍照片：隔一段时间拍一张 Redis 数据快照。
AOF 像记流水账：每次写操作都记下来，恢复时重新执行。

AOF 常见刷盘策略：

策略 说明
always 每次写都刷盘，最安全但最慢
everysec 每秒刷盘，常用折中方案
no 交给操作系统决定，性能好但风险更大

一句话总结：

RDB 恢复快但可能丢数据，AOF 更安全但文件更大、恢复更慢，生产常结合使用。

2. Redis key 过期后是怎么删除的？

【答】
Redis 过期 key 删除主要靠两种机制：

  1. 惰性删除：访问 key 时发现过期，再删除。
  2. 定期删除：Redis 定期抽样检查一批 key，删除过期 key。

【展开】

flowchart LR A["key 设置过期时间"] --> B{"之后是否被访问?"} B -->|被访问| C["惰性删除：发现过期就删"] B -->|没被访问| D["定期删除：后台抽样清理"]

为什么不用“到点立刻删除”？

如果每个 key 到期都立刻删除，需要维护大量定时任务。
key 很多时，会给 CPU 带来很大压力。

为什么只定期抽样，不全量扫描？

全量扫描成本太高，会影响 Redis 正常处理请求。

一句话总结：

Redis 过期删除不是到点立刻全删，而是惰性删除加定期抽样删除。

3. Redis 内存满了怎么办？

【答】
Redis 内存达到 maxmemory 后，会根据内存淘汰策略处理。

常见策略可以分成几类：

策略 大白话解释
noeviction 不淘汰，写入直接报错
allkeys-lru 所有 key 中淘汰最近最少使用的
volatile-lru 只在设置过期时间的 key 中按 LRU 淘汰
allkeys-random 所有 key 中随机淘汰
volatile-random 过期 key 中随机淘汰
volatile-ttl 优先淘汰快过期的 key
allkeys-lfu 所有 key 中淘汰访问频率低的
volatile-lfu 过期 key 中淘汰访问频率低的

【展开】 怎么选？

纯缓存场景：常用 allkeys-lru 或 allkeys-lfu。
只有部分 key 能淘汰：使用 volatile 相关策略，但要保证 key 设置了过期时间。
不能丢数据：用 noeviction，并做好监控和扩容。

面试表达：

Redis 内存满了不能只说加机器。
要先看 maxmemory、淘汰策略、key 大小、热 key、是否有大对象，再决定优化数据结构、拆分 key、扩容或调整淘汰策略。

一句话总结：

Redis 内存满了会按淘汰策略处理；纯缓存通常用 LRU/LFU，不能丢数据就不能随便淘汰。

1. 什么是缓存穿透、击穿、雪崩？怎么解决？

【答】
三者都是缓存失效导致数据库压力变大的问题，但原因不同。

问题 现象 常见解决
缓存穿透 查不存在的数据，请求直接打到数据库 缓存空值、布隆过滤器、参数校验
缓存击穿 一个热点 key 失效，大量请求同时打数据库 互斥锁、逻辑过期、热点 key 不过期
缓存雪崩 大量 key 同时失效或 Redis 故障 过期时间加随机值、限流降级、集群高可用

【展开】

flowchart TB subgraph pen["穿透：查不存在"] A1["请求非法 key"] --> A2["缓存 miss"] A2 --> A3["数据库也没有"] A3 --> A4["每次都打库"] end subgraph brk["击穿：热点过期"] B1["热点 key 刚好过期"] --> B2["大量并发 miss"] B2 --> B3["一起打同一条数据"] end subgraph ava["雪崩：大面积失效"] C1["大量 key 同时过期 / Redis 挂"] --> C2["请求瞬间压到数据库"] end

缓存穿透：

请求查 id=-1，缓存没有，数据库也没有。
如果大量这种请求进来，每次都打数据库。

看图重点：缓存穿透的本质是“缓存和数据库都没有”，所以请求会绕过缓存不断压到数据库。

解决：

缓存空对象，但要设置较短过期时间。
使用布隆过滤器提前判断数据是否可能存在。
做参数合法性校验。

布隆过滤器注意：

布隆过滤器说“不存在”时可以认为一定不存在。
它说“可能存在”时，不代表数据库里一定有，只是允许请求继续往后查。
所以布隆过滤器能拦住大量非法 key，但不能替代数据库查询。

缓存击穿：

一个超级热点 key 刚好过期，大量请求同时查它。
缓存没有，所有请求一起打数据库。

解决：

加互斥锁，只让一个线程查数据库并重建缓存。
使用逻辑过期，先返回旧数据，后台异步刷新。
热点 key 设置较长过期时间或不过期。

缓存雪崩：

大量 key 同一时间失效，或者 Redis 整体不可用。
请求瞬间压到数据库。

解决：

过期时间加随机值，避免同一时间大面积过期。
Redis 做高可用。
接口做限流、降级、熔断。

一句话总结：

穿透是查不存在，击穿是热点 key 过期，雪崩是大量 key 失效或 Redis 挂了。

2. 如何保证数据库和缓存一致性？

【答】
缓存和数据库很难做到绝对强一致，常见目标是尽量保证最终一致。

最常用方案是：

先更新数据库，再删除缓存。

【展开】 为什么不是先删缓存再更新数据库？

线程 A 先删缓存，还没来得及更新数据库。
线程 B 查询发现缓存没有，于是读旧数据库并写回缓存。
线程 A 再更新数据库。
结果缓存里还是旧数据。

为什么更新数据库后删除缓存更常用？

数据库是最终数据源。
先保证数据库更新成功，再删除缓存。
下次查询缓存没有，就会从数据库加载新数据。
flowchart LR U["更新数据库"] --> D["删除缓存"] D --> Q["下次查询 miss"] Q --> L["从数据库加载新值写回缓存"]

常见增强方案：

方案 说明
延迟双删 更新数据库后删缓存，延迟一会儿再删一次
MQ 重试删除 删除缓存失败时发消息重试
监听 Binlog 通过 Canal 等监听数据库变更，再删除或更新缓存
设置过期时间 即使删除失败，缓存最终也会过期

面试表达：

缓存一致性要结合业务要求。
一般读多写少场景使用先更新数据库再删除缓存，并配合重试和过期时间保证最终一致。
强一致要求很高的场景，不应该完全依赖缓存。

一句话总结：

缓存一致性没有银弹，常见做法是更新数据库后删除缓存，再用重试、过期时间或 Binlog 保证最终一致。

动画辅助：动画/08-Redis.html → 专题「03 分布式锁」

1. Redis 分布式锁怎么实现？

【答】
Redis 分布式锁常用命令：

SET lockKey uniqueValue NX EX seconds

含义：

参数 作用
NX key 不存在才设置成功
EX 设置过期时间
uniqueValue 当前线程/请求的唯一标识

【展开】 为什么要设置过期时间？

如果业务拿到锁后服务宕机，没有过期时间，锁永远不释放。
其他线程就永远拿不到锁。

为什么加锁要原子完成？

如果先 setnx，再 expire，中间服务宕机，就可能留下没有过期时间的死锁。
所以要用一条 SET 命令同时完成加锁和设置过期时间。

一句话总结：

Redis 锁的基础写法是 SET NX EX，一条命令完成抢锁和设置过期时间。

2. Redis 分布式锁如何防止误删？

【答】
防止误删的关键是：释放锁时先判断锁是不是自己的，再删除。

不能直接 del lockKey。

【展开】 误删场景：

线程 A 拿到锁，锁过期了。
线程 B 拿到同一把锁。
线程 A 执行完后直接 del，把线程 B 的锁删了。
sequenceDiagram participant A as 线程A participant R as Redis participant B as 线程B A->>R: SET lock = A NX EX Note over R: A 的锁过期 B->>R: SET lock = B NX EX A->>R: DEL lock（误删） Note over B: B 的锁被 A 删掉了

正确做法：

加锁时写入唯一值。
释放锁时比较 value 是否等于自己的唯一值。
相等才删除。

为什么释放锁要用 Lua？

判断 value 和删除 key 必须是原子操作。
如果先 get 判断，再 del 删除，中间锁可能已经过期并被别人拿到。
Lua 脚本可以让判断和删除在 Redis 里一次完成。

Lua 逻辑：

if redis.call("get", KEYS[1]) == ARGV[1] then
  return redis.call("del", KEYS[1])
else
  return 0
end

一句话总结：

防误删靠唯一值，释放锁靠 Lua 保证“判断 + 删除”原子执行。

3. Redisson 分布式锁原理是什么？

【答】
Redisson 是 Redis 分布式锁的常用客户端实现。

它帮我们封装了加锁、解锁、可重入、自动续期等能力。

【展开】 Redisson 锁常见特点：

能力 说明
可重入 同一线程重复加锁不会死锁
自动续期 看门狗机制给锁续期
Lua 解锁 保证判断锁归属和删除的原子性
等待获取 支持尝试等待一段时间获取锁

看门狗是什么？

线程拿到锁后，如果业务还没执行完，Redisson 会定期帮这把锁续期。
避免业务没执行完，锁先过期，被其他线程拿走。

面试注意：

如果调用 lock.lock(10, TimeUnit.SECONDS) 指定了固定过期时间，看门狗通常不会自动续期。
如果业务执行时间可能不确定，要谨慎设置锁时间或使用默认看门狗机制。

一句话总结：

Redisson 在 SET NX EX 的基础上，补了可重入、Lua 安全解锁和看门狗续期。

一句话总结：

1. MySQL 索引是什么？为什么能提高查询速度？

【答】
索引可以理解成数据库表的“目录”。

没有索引时，MySQL 可能要从头到尾扫描整张表。

有索引后，MySQL 可以先通过索引快速定位到目标数据，减少扫描行数。

【展开】

flowchart LR A["查询条件"] --> B{"有没有合适索引?"} B -->|没有| C["全表扫描"] B -->|有| D["走索引定位"] D --> E["读取目标数据"]

例子：

select * from user where phone = '13800138000';

如果 phone 没有索引，可能要扫很多行。

如果 phone 有索引，可以更快定位到对应记录。

面试表达：

索引提升查询速度的本质是减少扫描范围。
但索引不是越多越好，索引会占空间，并且插入、更新、删除时也要维护索引。

一句话总结：

索引像目录，能减少扫描行数；但索引也有维护成本。

2. B+ 树索引为什么适合数据库？

【答】
MySQL InnoDB 常用 B+ 树索引。

B+ 树适合数据库，主要因为：

  1. 树高比较低，磁盘 IO 次数少。
  2. 叶子节点有序，适合范围查询。
  3. 非叶子节点主要存索引键，可以放更多索引项。

【展开】

flowchart TB R["根节点"] --> N1["索引页"] R --> N2["索引页"] N1 --> L1["叶子节点：数据/主键"] N1 --> L2["叶子节点：数据/主键"] N2 --> L3["叶子节点：数据/主键"] L1 -. "链表相连，适合范围查询" .-> L2 L2 -. "链表相连" .-> L3

为什么不是普通二叉树？

普通二叉树层数可能很高。
数据库数据在磁盘上，树越高，磁盘 IO 次数越多。
B+ 树一个节点可以存很多索引项，层数更低。

为什么适合范围查询？

B+ 树叶子节点之间有顺序链表。
找到起点后，可以顺着叶子节点继续向后扫。

一句话总结：

B+ 树层高低、磁盘 IO 少、叶子节点有序，所以很适合数据库索引。

3. 聚簇索引和非聚簇索引有什么区别？

【答】
InnoDB 中，聚簇索引的叶子节点存的是整行数据。

非聚簇索引的叶子节点存的是主键值。

所以通过普通索引查数据时，可能需要先查到主键，再用主键回到聚簇索引查整行，这个过程叫回表。

【展开】

索引 叶子节点存什么
聚簇索引 整行数据
非聚簇索引 主键值

流程：

按普通索引查到主键
→ 再按主键查聚簇索引
→ 拿到整行数据
flowchart LR A["普通索引 phone"] --> B["查到主键 id"] B --> C["回到聚簇索引"] C --> D["拿到整行数据"]

覆盖索引是什么？

如果查询字段都在普通索引里，不需要回表，就叫覆盖索引。

一句话总结：

聚簇索引叶子节点就是数据，普通索引叶子节点是主键；普通索引查整行可能要回表。

4. 联合索引的最左前缀原则是什么？

【答】
联合索引会按照定义的字段顺序建立索引。

最左前缀原则就是：查询条件要从联合索引最左边的字段开始连续使用，索引才能更好生效。

【展开】 例如索引：

index idx_user_status_time(user_id, status, create_time)

能较好利用索引：

where user_id = ?
where user_id = ? and status = ?
where user_id = ? and status = ? and create_time > ?

不符合最左前缀：

where status = ?
where create_time > ?
where status = ? and create_time > ?

原因：

联合索引是先按 user_id 排，再按 status 排，再按 create_time 排。
如果跳过最左边的 user_id，后面的字段整体就不是全局有序的。

一句话总结：

联合索引要从最左字段开始连续使用，跳过前面的字段，后面的字段通常很难充分利用索引。

5. 索引失效有哪些常见原因？

【答】
常见索引失效原因：

原因 示例
对索引列使用函数 where date(create_time) = ?
隐式类型转换 字符串字段用数字查询
左模糊查询 like '%abc'
联合索引不满足最左前缀 (a,b,c) 直接按 b 查
范围查询后面的列无法充分使用 a = ? and b > ? and c = ?
or 使用不当 两边条件不都有合适索引
数据区分度太低 性别字段单独建索引效果差

【展开】 例子：

select * from user where phone = 13800138000;

如果 phone 是字符串类型，这样写可能触发隐式转换。

更稳写法：

select * from user where phone = '13800138000';

面试表达：

索引不是建了就一定会用，要结合 SQL 写法、字段类型、联合索引顺序和执行计划判断。

一句话总结：

索引失效本质上是 SQL 写法破坏了索引的有序性或让 MySQL 无法快速定位。

6. 什么是索引下推？

【答】
索引下推，也叫 ICP，Index Condition Pushdown。

它的作用是：在存储引擎扫描索引时，尽量先用索引里已有的字段过滤数据，减少回表次数。

简单说：

能在索引层判断掉的数据，就不要回表后再判断。

【展开】 假设有联合索引：

index idx_name_age(name, age)

SQL：

select * from user
where name like '张%' and age = 18;

这里 name like '张%' 可以用到联合索引的最左字段。

如果没有索引下推，流程可能是：

先根据 name like '张%' 找到一批索引记录
→ 每条都回表拿整行数据
→ 再判断 age 是否等于 18

有索引下推后，流程变成：

先根据 name like '张%' 找到一批索引记录
→ 在索引里直接判断 age 是否等于 18
→ 符合条件的再回表
flowchart LR A["扫描联合索引"] --> B["先判断 name 条件"] B --> C["在索引层继续判断 age 条件"] C --> D{"是否满足?"} D -->|满足| E["回表取整行"] D -->|不满足| F["直接过滤，减少回表"]

为什么能减少回表？

因为 age 字段也在联合索引 idx_name_age 里。
MySQL 不需要回到聚簇索引拿整行，就能先判断 age 条件。
不符合条件的记录，直接在索引层过滤掉。

面试表达：

索引下推不是让索引一定生效，也不是替代最左前缀原则。
它是在已经走索引扫描的基础上，把能在存储引擎层判断的条件提前判断，减少回表次数。
在 InnoDB 中，索引下推主要用于二级索引扫描场景，因为二级索引命中后如果要取整行数据，通常会产生回表。

一句话总结：

索引下推就是把部分 where 条件下推到存储引擎的索引扫描阶段，先过滤，再回表。

1 是什么 什么是事务？ACID 是什么？ 四大特性
2 是什么 MySQL 事务隔离级别有哪些？ 读未提交、读已提交、可重复读、串行化

1. 什么是事务？ACID 是什么？

【答】
事务是一组数据库操作，要么都成功，要么都失败。

ACID 是事务的四个特性：

特性 含义
Atomicity 原子性 要么全成功，要么全失败
Consistency 一致性 事务前后数据满足业务规则
Isolation 隔离性 并发事务之间互不干扰到不合理程度
Durability 持久性 事务提交后数据要持久保存

【展开】 例子：转账。

A 扣 100
B 加 100

这两个操作必须放在一个事务里：

不能 A 扣钱成功，B 加钱失败。

一句话总结：

事务就是把一组操作绑在一起，保证它们按规则一起成功或一起失败。

2. MySQL 事务隔离级别有哪些？

【答】
MySQL 有四种事务隔离级别：

隔离级别 大白话理解
Read Uncommitted 能读到别人没提交的数据
Read Committed 只能读到别人已提交的数据
Repeatable Read 同一事务中多次读结果尽量一致，MySQL 默认
Serializable 串行执行，隔离最强，并发最低

【展开】 隔离越强，并发能力通常越弱。

读未提交：并发高，但问题多。
读已提交：避免脏读。
可重复读：避免不可重复读，MySQL InnoDB 默认。
串行化：最安全，但性能最差。

一句话总结：

隔离级别是在数据正确性和并发性能之间做取舍，MySQL InnoDB 默认是可重复读。

3. 什么是脏读、不可重复读、幻读？

【答】
这是事务并发下可能出现的三个问题。

问题 大白话解释
脏读 读到了别人还没提交的数据
不可重复读 同一行数据，前后两次读结果不一样
幻读 同一个范围查询，前后读到的行数不一样

【展开】 脏读：

事务 A 修改数据但没提交。
事务 B 读到了这个修改。
事务 A 回滚。
事务 B 读到的就是脏数据。

不可重复读：

事务 A 第一次读 user=张三。
事务 B 把张三改成李四并提交。
事务 A 第二次读同一行变成李四。

幻读：

事务 A 查询 age > 18 有 10 行。
事务 B 插入一条 age=20 的数据并提交。
事务 A 再查同一范围，像多出了一条幻影。

面试补充：

在 InnoDB 的可重复读隔离级别下，普通 select 是快照读，通常通过 MVCC 保证同一事务内看到一致快照。
select for update、update、delete 这类当前读会读最新数据，并可能通过间隙锁、临键锁来避免并发插入造成的问题。
所以讲幻读时要区分快照读和当前读。

一句话总结：

脏读读到未提交，不可重复读关注同一行变化，幻读关注范围内行数变化。

4. MVCC 是什么？解决了什么问题？

【答】
MVCC 是多版本并发控制。

它通过保存数据的多个版本，让读操作不用总是和写操作互相阻塞。

InnoDB 中快照读通常依赖 MVCC 实现。

【展开】 可以这样理解：

写操作生成新版本。
读操作根据自己的事务视图，读取它应该看到的版本。
flowchart LR A["事务 A 开始"] --> B["生成 ReadView"] C["数据多个版本"] --> D["根据可见性规则选择版本"] B --> D D --> E["返回事务 A 能看到的数据"]

MVCC 主要解决：

提高读写并发。
减少读写之间的阻塞。
支持快照读。

面试表达：

MVCC 不是锁，它是通过版本链和 ReadView 判断当前事务能看到哪个版本的数据。
普通 select 多数情况下走快照读，update/delete/select for update 这类当前读会涉及锁。

一句话总结：

MVCC 让读操作看到合适的数据版本，从而提高并发读写能力。

5.3 MySQL 锁

总览 MySQL 锁重点是：锁住什么、什么时候锁、锁不当会带来什么问题。

序号 题型 面试题 重点

1. MySQL 中有哪些锁？

【答】
MySQL 锁可以从不同角度分类。

常见面试回答：

分类 说明
表锁 锁整张表
行锁 锁具体行
间隙锁 锁索引记录之间的间隙
临键锁 行锁 + 间隙锁
共享锁 读锁
排他锁 写锁
意向锁 表级锁，用来表示表里某些行可能被锁

【展开】 面试重点一般在 InnoDB：

InnoDB 支持行锁。
但行锁是基于索引实现的。
如果 SQL 没有用到索引，可能导致锁范围扩大。

一句话总结：

MySQL 锁不要只背名字，核心要知道锁范围和是否命中索引。

2. 行锁、表锁、间隙锁、临键锁分别是什么？

【答】
这几个锁主要区别是锁定范围。

锁 锁什么
表锁 整张表
行锁 某一行索引记录
间隙锁 两条索引记录之间的范围
临键锁 行锁 + 间隙锁

【展开】 间隙锁主要是为了防止幻读相关问题。

例子：

表里有 id=10 和 id=20。
锁住 10 到 20 之间的间隙后，其他事务就不能往这个间隙插入 id=15。
flowchart LR R10["记录 10"] --- G["间隙 (10,20)"] --- R20["记录 20"] G -.->|间隙锁拦住| X["插入 15 被拒绝"] R20 -.->|临键锁 = 行 + 间隙| Next["下一段范围"]

临键锁：

既锁住已有记录，也锁住记录前后的间隙。

面试表达：

InnoDB 在可重复读隔离级别下，为了解决范围查询中的并发插入问题，会用到间隙锁和临键锁。
实际锁范围要结合索引和执行计划判断。

一句话总结：

行锁锁记录，间隙锁锁范围，临键锁是记录加范围。

3. MySQL 死锁怎么产生？怎么排查？

【答】
MySQL 死锁通常是两个事务互相持有对方需要的锁。

比如：

事务 A 锁住订单 1，等待订单 2。
事务 B 锁住订单 2，等待订单 1。
两个事务互相等待，形成死锁。

【展开】 排查方式：

show engine innodb status;

重点看：

LATEST DETECTED DEADLOCK

可以看到最近一次死锁涉及的事务、SQL、锁等待信息。

避免方式：

多个事务按固定顺序更新数据。
事务尽量短，减少锁持有时间。
SQL 尽量命中索引，减少锁范围。
避免大事务和复杂交叉更新。

一句话总结：

MySQL 死锁靠 innodb status 看现场，优化重点是固定加锁顺序、缩短事务、命中索引。

4. update 没有命中索引会有什么问题？

【答】
update 没有命中索引时，MySQL 可能扫描更多记录，锁范围也可能扩大。

严重时会导致大量行被锁住，影响并发。

【展开】 例子：

update user set status = 1 where phone = '13800138000';

如果 phone 没有索引，MySQL 可能全表扫描。

影响：

扫描行数变多。
锁等待变多。
事务执行时间变长。
并发更新容易阻塞。

面试表达：

InnoDB 行锁基于索引实现。
更新条件如果没有命中索引，可能导致扫描大量记录并扩大锁影响范围，所以更新条件字段尤其要注意索引。

一句话总结：

update 不走索引，不只是慢，还可能扩大锁范围，拖垮并发。

3. order by / group by 为什么会慢？怎么优化？

【答】
order by 和 group by 慢，常见原因是不能利用索引完成排序或分组，导致额外排序或临时表。

【展开】 常见现象：

Using filesort
Using temporary

优化思路：

让排序字段尽量走索引。
where 条件和 order by 字段设计合适的联合索引。
减少排序数据量。
避免 select *。
能分页先缩小数据范围。

例子：

select id, title
from article
where category_id = ?
order by create_time desc
limit 20;

可以考虑联合索引：

index(category_id, create_time)

一句话总结：

排序和分组慢，常见是没用好索引导致 filesort 或 temporary，优化重点是减少参与排序的数据量。

4. 分页查询很慢怎么优化？

【答】
分页慢通常是深分页问题。

比如：

select * from orders order by id limit 1000000, 20;

MySQL 要跳过前面 1000000 条，再取 20 条，成本很高。

【展开】 常见优化：

方案 说明
基于上一页最大 ID where id > lastId limit 20
延迟关联 先查主键，再回表查详情
覆盖索引 查询字段尽量从索引直接拿
限制深翻页 产品上限制只能翻前 N 页

一句话总结：

深分页慢是因为跳过的数据太多，优化重点是减少扫描和回表。

5.5 MySQL 日志与主从

总览 日志和主从是 MySQL 可靠性、高可用和数据恢复的基础。

序号 题型 面试题 重点
1 对比 binlog、redo log、undo log 有什么区别？ 复制、恢复、回滚
2 原理 MySQL 主从复制原理是什么？ binlog、relay log

1. binlog、redo log、undo log 有什么区别？

【答】
三个日志作用不同：

日志 作用 层级
binlog 记录逻辑变更，用于主从复制和数据恢复 MySQL Server 层
redo log 保证已提交事务崩溃后能恢复 InnoDB
undo log 支持事务回滚和 MVCC InnoDB

【展开】 大白话：

binlog：记录做了什么，用于复制和恢复。
redo log：保证提交后的数据不丢。
undo log：后悔药，用于回滚，也支持 MVCC 读取旧版本。

一句话总结：

binlog 管复制和恢复，redo log 管崩溃恢复，undo log 管回滚和多版本读。

2. MySQL 主从复制原理是什么？

【答】
MySQL 主从复制主要依赖 binlog。

流程：

主库写入数据并记录 binlog
→ 从库 IO 线程拉取 binlog
→ 写入 relay log
→ 从库 SQL 线程重放 relay log
→ 从库数据追上主库

【展开】

flowchart LR A["Master 写入"] --> B["binlog"] B --> C["Slave IO 线程拉取"] C --> D["relay log"] D --> E["Slave SQL 线程重放"] E --> F["从库数据更新"]

主从复制用途：

读写分离。
数据备份。
故障切换基础。

一句话总结：

主从复制就是从库拉取主库 binlog，再重放日志让数据保持一致。

3. 主从延迟是什么？怎么解决？

【答】
主从延迟就是主库已经提交了数据，但从库还没同步到。

这时如果读从库，可能读到旧数据。

【展开】 常见原因：

主库写入压力大。
从库机器性能差。
从库 SQL 线程重放慢。
大事务或大批量更新。
网络延迟。

解决思路：

方案 说明
核心读走主库 刚写完马上读的关键数据直接读主
半同步复制 降低数据丢失风险，但会影响性能
并行复制 提升从库重放能力
拆分大事务 避免从库长时间追不上
监控延迟 延迟过高时告警或临时切主读

面试表达：

主从延迟不能只靠技术硬扛。
对一致性要求高的读请求要走主库，允许短暂不一致的读请求才走从库。

一句话总结：

主从延迟会导致读到旧数据，解决要结合业务一致性要求决定读主还是读从。

5.6 分库分表

总览 分库分表不是一上来就做，它是单库单表扛不住之后的架构手段。

序号 题型 面试题 重点
1 是什么 为什么需要分库分表？ 容量、性能、并发瓶颈
2 对比 分库分表有哪些常见方式？ 垂直拆分、水平拆分
3 场景 分库分表后会带来哪些问题？ ID、事务、Join、扩容
4 场景 分库分表后的分页、排序、查询怎么处理？ shard key、聚合、冗余

1. 为什么需要分库分表？

【答】
分库分表是为了解决单库、单表在数据量和并发量变大后的瓶颈。

常见瓶颈：

单表数据太大，查询和维护变慢。
单库连接数、CPU、IO 压力太高。
写入并发太大，单库扛不住。
数据增长太快，后续扩展困难。

【展开】 例子：

订单表有几千万甚至上亿数据。
所有订单都在一张表里，查询、索引维护、归档、备份都会越来越重。

分库分表后的思路：

把一张大表的数据，按规则拆到多张表或多个库里。
让每个库、每张表只承担一部分数据和流量。
flowchart LR A["订单表 orders"] --> B["orders_0"] A --> C["orders_1"] A --> D["orders_2"] A --> E["orders_3"]

面试表达：

分库分表通常是业务发展到一定规模后的手段，不是项目一开始就必须做。
优先应该先做好索引、SQL 优化、缓存、读写分离和归档；这些还不够时，再考虑分库分表。

一句话总结：

分库分表是为了把单点数据库压力拆散，但它会明显增加系统复杂度。

2. 分库分表有哪些常见方式？

【答】
常见方式有两类：

  1. 垂直拆分：按业务或字段拆。
  2. 水平拆分：按数据行拆。

【展开】

方式 大白话解释 例子
垂直分库 不同业务放不同库 用户库、订单库、商品库
垂直分表 一张表的字段拆成多张表 用户基础表、用户扩展表
水平分库 同一张表的数据按规则分到多个库 order_db_0、order_db_1
水平分表 同一张表的数据按规则分到多张表 orders_0、orders_1

水平拆分常见规则：

按 user_id 取模。
按 order_id 取模。
按时间范围拆分。
按地区或租户拆分。

例子：

order_id % 4 = 0 → orders_0
order_id % 4 = 1 → orders_1
order_id % 4 = 2 → orders_2
order_id % 4 = 3 → orders_3

一句话总结：

垂直拆分是按业务或字段拆，水平拆分是按数据行拆。

3. 分库分表后会带来哪些问题？

【答】
分库分表能拆压力，但会带来很多新问题。

常见问题：

问题 说明
分布式 ID 自增主键不能直接全局唯一
跨库 Join 数据分散后，Join 很难直接做
分布式事务 一次操作跨多个库，事务复杂
分页排序 多个分片都要查，再合并排序
扩容迁移 分片规则变化后，数据迁移成本高
查询路由 必须知道数据在哪个库表
全局唯一约束 单库唯一索引不能直接约束全局

【展开】 为什么分片键重要？

如果用 user_id 分片，按 user_id 查订单很快。
但如果按手机号、订单状态、创建时间查，可能不知道数据在哪个分片，只能扫多个分片。

常见解决思路：

分布式 ID：雪花算法、号段模式。
跨库 Join：字段冗余、数据宽表、应用层组装。
分布式事务：最终一致性、MQ、Seata、TCC。
分页排序：限制深分页、按分片查询后合并、使用 ES。
扩容迁移：提前规划分片数，或使用支持平滑扩容的中间件。

面试表达：

分库分表不是免费优化，它会把数据库压力问题转成架构复杂度问题。
所以要明确拆分键、查询模式、事务边界和扩容方案。

一句话总结：

分库分表后最大的问题不是怎么拆，而是拆完以后怎么查、怎么事务一致、怎么扩容。

4. 分库分表后的分页、排序、查询怎么处理？

【答】
分库分表后，最理想的查询是带上分片键，直接路由到单个库表。

如果不带分片键，就可能需要查多个分片，再在应用层合并结果，成本会高很多。

【展开】 查询分三类：

查询类型 处理方式
带分片键查询 直接路由到目标库表，最推荐
不带分片键查询 多分片查询后合并，成本高
复杂搜索 考虑冗余表、宽表或 ES

分页排序难点：

每个分片都有自己的前 N 条。
全局前 N 条需要多个分片都查出来，再合并排序。
offset 越大，多个分片扫描和合并成本越高。

优化思路：

核心查询尽量带分片键。
避免深分页。
使用游标翻页。
冗余查询字段，减少跨分片查。
复杂检索同步到 ES。
报表类查询走离线数仓或宽表。

例子：

用户查自己的订单：带 user_id，可以直接路由。
后台按订单状态查全站订单：可能跨多个分片，适合做冗余索引表、ES 或后台报表方案。

一句话总结：

分库分表后的查询设计，核心是尽量带分片键；不带分片键的全局分页排序要谨慎设计。

1. RabbitMQ 的核心组件有哪些？

【答】
RabbitMQ 核心组件有：

组件 作用
Producer 生产者，负责发送消息
Exchange 交换机，负责按规则路由消息
Queue 队列，负责存储消息
Consumer 消费者，负责消费消息
Binding 绑定关系，把交换机和队列连起来
RoutingKey 路由键，生产者发送消息时指定
BindingKey 绑定键，队列绑定交换机时指定

【展开】

flowchart LR P["Producer"] --> E["Exchange"] E -->|Binding| Q["Queue"] Q --> C["Consumer"]

大白话理解：

Producer 像寄件人。
Exchange 像分拣中心。
Queue 像快递柜。
Consumer 像取件人。
Binding 规定分拣中心把哪些包裹放到哪个快递柜。

面试表达：

RabbitMQ 中生产者通常不直接发送到队列，而是发送到交换机。
交换机根据类型、routingKey 和 bindingKey，把消息路由到一个或多个队列。
消费者从队列中拉取或接收消息进行处理。

一句话总结：

RabbitMQ 的核心链路是：生产者发给交换机，交换机路由到队列，消费者从队列消费。

2. RabbitMQ 一条消息从生产到消费的流程是什么？

【答】
一条消息的完整流程是：

生产者发送消息
→ 交换机接收消息
→ 根据路由规则投递到队列
→ 消费者获取消息
→ 消费成功后发送 ACK
→ RabbitMQ 删除队列中的消息

【展开】

flowchart TB A["生产者发送消息"] --> B["Exchange 接收"] B --> C["根据路由规则匹配队列"] C --> D["消息进入 Queue"] D --> E["Consumer 消费"] E --> F["发送 ACK"] F --> G["Broker 删除消息"]

如果消费失败怎么办？

如果消费者没有 ACK，RabbitMQ 会认为消息没有被正确处理。
连接断开或消费者异常时，消息可能重新回到队列，等待其他消费者处理。

面试表达：

RabbitMQ 的消息链路要关注三个确认点：生产者是否成功发到 Broker，消息是否成功路由到队列，消费者是否成功消费并 ACK。

一句话总结：

RabbitMQ 消息不是发出去就完事，要看是否到达交换机、是否进入队列、是否被消费者确认。

6.2 交换机与队列

总览 交换机决定消息怎么路由。

序号 题型 面试题 重点
1 是什么 RabbitMQ 有哪些交换机类型？ direct、topic、fanout、headers
2 对比 direct、topic、fanout 有什么区别？ 精确匹配、通配符、广播

1. RabbitMQ 有哪些交换机类型？

【答】
RabbitMQ 常见交换机类型有：

类型 作用
direct 根据 routingKey 精确匹配
topic 根据 routingKey 通配符匹配
fanout 广播到所有绑定队列
headers 根据消息头匹配，较少用

【展开】 可以这样理解：

direct：按具体门牌号投递。
topic：按规则匹配投递。
fanout：不看路由键，绑定的队列都发一份。
headers：按消息头条件匹配，实际项目不常用。

一句话总结：

交换机负责消息路由，最常用的是 direct、topic、fanout。

2. direct、topic、fanout 有什么区别？

【答】
三者区别主要在路由方式。

交换机 路由规则 典型场景
direct routingKey 和 bindingKey 完全相等 精确业务事件
topic routingKey 支持 * 和 # 通配符 按业务模块分类订阅
fanout 不看 routingKey，直接广播 广播通知

【展开】 direct：

routingKey = order.created
bindingKey = order.created
完全匹配才投递。

topic：

routingKey = order.created.pay
bindingKey = order.*
或 order.#
按通配符匹配。

fanout：

只要队列绑定了这个交换机，就都会收到消息。

通配符说明：

通配符 含义
* 匹配一个单词
# 匹配零个或多个单词

一句话总结：

direct 是精确匹配，topic 是模式匹配，fanout 是广播。

6.3 消息可靠性

总览 消息可靠性要按链路看，不要只说“开启持久化”。

生产者到交换机不能丢
→ 交换机到队列不能丢
→ 队列存储不能丢
→ 消费者处理不能丢
序号 题型 面试题 重点
1 场景 RabbitMQ 如何保证消息不丢失？ 全链路可靠
2 原理 publisher confirm 和 return 机制是什么？ 生产端确认
3 场景 消息持久化怎么做？ exchange、queue、message

动画辅助：动画/09-消息队列.html →「03 三段不丢」

1. RabbitMQ 如何保证消息不丢失？

【答】
要从四个环节保证：

  1. 生产者发送到 Broker：开启 publisher confirm。
  2. 交换机路由到队列：开启 return 机制或备份交换机。
  3. 队列保存消息：交换机、队列、消息都持久化。
  4. 消费者处理消息：手动 ACK，处理成功后再确认。

【展开】

flowchart LR A["生产者"] -->|confirm| B["Exchange"] B -->|return/备份交换机| C["Queue"] C -->|持久化| D["磁盘"] C --> E["Consumer"] E -->|手动 ACK| C

看图重点：消息可靠性不是只配一个 ACK，而是生产者、Broker、消费者三段都要有兜底。

面试表达：

消息可靠性不是单点配置，而是生产端确认、路由失败处理、消息持久化、消费端手动 ACK 组合起来保证。

注意：

即使做了持久化，也不是绝对零丢失。
比如消息还没刷盘 Broker 就宕机，仍然可能有风险。
所以关键业务还要结合业务表、消息表、重试和对账机制。

一句话总结：

RabbitMQ 防丢要看完整链路：发到没、路由到没、存住没、消费成功没。

2. publisher confirm 和 return 机制是什么？

【答】
publisher confirm 用来确认消息是否成功到达交换机。

return 机制用来处理消息到达交换机后，却没有路由到任何队列的情况。

【展开】

机制 解决什么问题
confirm 生产者发出的消息有没有到达 exchange
return 消息到达 exchange 后，有没有成功路由到 queue

注意：return 回调通常需要生产者发送消息时开启 mandatory，否则消息路由不到队列时可能直接被 Broker 丢弃，不一定回调给生产者。

流程：

flowchart TB A["Producer"] --> B["Exchange"] B --> C{"是否收到?"} C -->|是| D["confirm ack"] C -->|否| E["confirm nack"] B --> F{"是否路由到队列?"} F -->|否| G["return callback"]

面试表达：

confirm 关注生产者到交换机，return 关注交换机到队列。
两者解决的是不同阶段的可靠性问题。

一句话总结：

confirm 保证消息到交换机，return 处理消息无法路由到队列。

3. 消息持久化怎么做？

【答】
RabbitMQ 持久化通常要三处都配置：

  1. 交换机持久化。
  2. 队列持久化。
  3. 消息持久化。

【展开】

对象 持久化作用
Exchange Broker 重启后交换机还在
Queue Broker 重启后队列还在
Message Broker 重启后消息尽量恢复

面试注意：

只设置队列持久化不够。
队列持久化只能保证队列结构还在，消息本身也要设置持久化。

还有一个现实点：

持久化会提升可靠性，但会牺牲一定性能。
关键业务开启持久化，非关键高吞吐场景要结合业务权衡。

一句话总结：

RabbitMQ 持久化要交换机、队列、消息一起看，不能只配一个。

6.4 消息消费问题

总览 消费端最常见三类问题：

消息重复了怎么办
→ 消费成功怎么确认
→ 消息积压了怎么办
序号 题型 面试题 重点
1 场景 RabbitMQ 如何防止消息重复消费？ 幂等
2 原理 消费者 ack 机制是什么？ 自动 ACK、手动 ACK
3 场景 消费堆积怎么办？ 扩容、限流、排查慢点
4 场景 RabbitMQ 如何保证消息顺序？ 单队列、单消费者、业务分片

1. RabbitMQ 如何防止消息重复消费？

【答】
RabbitMQ 不能保证业务天然不重复，防重复消费主要靠消费者做幂等。

常见做法：

使用业务唯一 ID。
消费前查是否处理过。
处理成功后记录消费状态。
重复消息直接忽略。

【展开】 为什么会重复？

消费者处理完业务，还没来得及 ACK 就宕机。
RabbitMQ 认为消息没消费成功，会重新投递。

解决方案：

方案 说明
唯一消息 ID 每条消息带唯一业务 ID
去重表 消费成功后记录消息 ID
业务状态判断 比如订单已支付就不重复扣款
Redis 去重 设置已处理标记，注意过期时间

面试表达：

消息队列一般追求至少一次投递，所以重复消费要在业务侧通过幂等解决。
不能假设 MQ 永远只投递一次。

一句话总结：

防重复消费的核心不是让 MQ 不重复，而是让业务重复执行也不会出错。

2. 消费者 ack 机制是什么？

【答】
ACK 是消费者告诉 RabbitMQ：这条消息我已经处理完成了。

如果开启自动 ACK，消息一投递给消费者就算成功，消费者后面异常也可能丢消息。

生产更常用手动 ACK：业务处理成功后再确认。

【展开】

模式 说明
自动 ACK RabbitMQ 投递后立即认为消费成功
手动 ACK 消费者业务处理成功后主动确认
nack/reject 消费失败，拒绝消息，可选择是否重新入队

处理逻辑：

业务成功：basicAck。
临时失败：可以 nack 并重新入队，或进入重试机制。
无法处理：不要无限重试，可以进死信队列。

面试注意：

手动 ACK 也不能乱用。
如果失败后一直 requeue，可能导致同一条坏消息反复消费，形成死循环。

一句话总结：

ACK 是消费成功确认，关键业务应该业务处理成功后再手动 ACK。

3. 消费堆积怎么办？

【答】
消费堆积就是消息进入队列的速度大于消费者处理速度。

排查思路：

先看生产速度
→ 再看消费速度
→ 再看消费者是否异常
→ 最后决定扩容、限流或优化消费逻辑

【展开】 常见原因：

原因 说明
消费者处理慢 数据库慢 SQL、远程接口慢、代码耗时
消费者数量不足 消费能力不够
消费者异常 消费失败反复重试
突发流量 生产者短时间发送太多
单队列限制 一个队列消费能力有限

处理方式：

临时扩容消费者。
优化消费者慢逻辑。
增加预取配置合理性。
对生产端限流。
拆分队列或按业务分片。
坏消息进入死信队列，避免反复阻塞。

面试表达：

消费堆积不能只说加消费者。
如果瓶颈在数据库或下游接口，加消费者可能把下游压垮。
要先定位慢在哪里，再决定扩容、限流还是优化。

一句话总结：

消费堆积本质是生产快于消费，先定位瓶颈，再扩容或限流。

4. RabbitMQ 如何保证消息顺序？

【答】
RabbitMQ 要保证严格顺序，核心是让同一类需要有序的消息进入同一个队列，并由同一个消费者顺序处理。

简单说：

同一个业务对象的消息，不能被多个消费者并发乱序处理。

【展开】 为什么会乱序？

多个队列会并行。
多个消费者会并行。
一个消费者处理慢，另一个消费者处理快，也可能导致业务结果乱序。

常见方案：

方案 说明
单队列单消费者 顺序最稳，但吞吐低
按业务 key 分片 同一个订单 ID 的消息进入同一个队列
消费端加状态校验 不符合状态流转的消息暂缓或重试
业务幂等和补偿 防止乱序导致重复或错误更新

例子：

同一个订单的 创建订单 -> 支付成功 -> 发货 消息必须按顺序处理。
可以按 orderId 路由到固定队列，保证同一个 orderId 的消息由同一消费链路处理。

面试表达：

MQ 天然适合提高吞吐，但严格顺序会牺牲并发能力。
所以通常只保证同一个业务 key 内有序，不追求全局有序。

一句话总结：

RabbitMQ 顺序消费的关键是控制并发范围：同一个业务 key 进同一队列，由固定消费链路顺序处理。

6.5 延迟消息与死信队列

总览 延迟消息和死信队列常放一起问，典型场景是订单超时关闭。

序号 题型 面试题 重点
1 是什么 什么是死信队列？ 死信来源、DLX
2 场景 RabbitMQ 如何实现延迟消息？ TTL + DLX、插件
3 场景 延迟消息适合哪些场景？ 超时取消、延迟重试

动画辅助：动画/09-消息队列.html →「04 死信与延迟」

1. 什么是死信队列？

【答】
死信队列就是专门接收“正常队列处理不了的消息”的队列。

消息变成死信后，会被发送到死信交换机，再路由到死信队列。

【展开】 消息变成死信的常见情况：

情况 说明
消息被拒绝 nack/reject，并且不重新入队
消息过期 消息 TTL 到期还没被消费
队列满了 超过队列长度限制
flowchart LR A["普通队列"] --> B{"消息过期/被拒绝/队列满"} B --> C["死信交换机 DLX"] C --> D["死信队列"]

看图重点：死信队列不是单独凭空存在的，普通队列里的异常消息会先进入死信交换机，再路由到死信队列。

一句话总结：

死信队列就是异常消息的兜底去处，方便后续排查、补偿或延迟处理。

2. RabbitMQ 如何实现延迟消息？

【答】
RabbitMQ 常见延迟消息实现方式有两种：

  1. TTL + 死信交换机。
  2. 延迟消息插件。

【展开】 TTL + DLX 的思路：

消息先进入一个延迟队列。
消息在延迟队列里不被消费。
TTL 到期后变成死信。
死信被投递到真正的业务队列。
消费者从业务队列消费。
flowchart LR A["发送延迟消息"] --> B["延迟队列 TTL"] B -->|到期变死信| C["死信交换机"] C --> D["业务队列"] D --> E["消费者处理"]

两种方案对比：

方案 特点
TTL + DLX 不需要插件，但不同延迟时间管理较麻烦
延迟插件 使用更直接，但需要安装插件

面试注意：

如果把不同延迟时间的消息放在同一个 TTL 队列里，可能出现队头阻塞。
比如队头消息 30 分钟后过期，后面一条 5 秒后应处理的消息也要等队头先过期。
所以固定延迟可以用不同 TTL 队列；灵活延迟更适合延迟插件或其他调度方案。

一句话总结：

RabbitMQ 本身常用 TTL + 死信队列实现延迟，也可以用延迟插件更直接地实现。

3. 延迟消息适合哪些场景？

【答】
延迟消息适合“现在不处理，过一段时间再处理”的场景。

常见场景：

场景 说明
订单超时取消 下单后 30 分钟未支付自动取消
延迟重试 调用失败后过一会儿再试
定时提醒 到点发送通知
自动确认 收货后 N 天自动确认
资源释放 超时释放占用资源

【展开】 订单超时取消流程：

用户下单
→ 发送 30 分钟延迟消息
→ 30 分钟后消费者收到消息
→ 查询订单是否已支付
→ 未支付则关闭订单，已支付则忽略

注意：

延迟消息到期后仍然要查数据库状态。
不能因为收到延迟消息就直接取消订单。
因为用户可能已经支付成功。

一句话总结：

延迟消息常用于超时处理，但真正执行业务前一定要再次校验当前状态。

1. Kafka 的核心组件有哪些？为什么吞吐高？

【答】
Kafka 的核心组件有：

组件 作用
Producer 生产者，发送消息
Broker Kafka 服务节点
Topic 主题，消息的逻辑分类
Partition 分区，一个 Topic 可以拆成多个分区
Consumer 消费者，拉取消息

Kafka 吞吐高，主要因为：

顺序写磁盘

【展开】

flowchart TB P["Producer"] --> T["Topic"] T --> P0["Partition 0：分区内有序"] T --> P1["Partition 1：分区内有序"] T --> P2["Partition 2：分区内有序"] P0 --> C["Consumer Group 分摊消费"] P1 --> C P2 --> C

2. Kafka 如何保证消息可靠性？

【答】
Kafka 可靠性主要看三个点：

生产者有没有确认成功
Broker 有没有副本保存
消费者有没有正确提交 offset

【展开】 生产端：

配置 说明
acks=0 不等确认，性能高但容易丢
acks=1 leader 写入成功就确认
acks=all ISR 副本都确认后才算成功，可靠性更高

Broker 端：

Topic 可以设置多个副本。
leader 负责读写，follower 复制数据。
ISR 表示当前跟得上的副本集合。

消费端：

消费者处理完消息后再提交 offset。
如果先提交 offset 再处理业务，业务失败时消息可能丢。

一句话总结：

Kafka 可靠性要从生产确认、副本复制、消费 offset 三段一起看。

3. Kafka 如何处理重复消费和顺序消费？

【答】
Kafka 不应该假设消息永远只消费一次，业务侧要做幂等。

Kafka 的顺序性是分区级别的：

同一个 Partition 内消息有序。
不同 Partition 之间不保证全局有序。

【展开】 重复消费常见原因：

消费者处理完业务，还没提交 offset 就宕机。
重启后从旧 offset 继续消费，消息会再次被处理。

解决重复消费：

业务唯一 ID。
去重表。
状态机判断。
Redis 去重。
消费端幂等。

保证同一业务有序：

把同一个业务 key 的消息发到同一个 Partition。
比如同一个 orderId 的消息固定进入同一分区。

面试表达：

Kafka 适合高吞吐场景，但严格全局有序会牺牲并发。
实际项目通常只保证同一个业务 key 在同一分区内有序。

一句话总结：

Kafka 重复消费靠业务幂等，顺序消费靠同一业务 key 进入同一分区。

7.1 接口性能优化场景

总览 接口性能优化不是一上来就改代码，而是先定位慢在哪里。

序号 题型 面试题 重点
1 排查 一个接口响应很慢，你怎么排查？ 链路拆解
2 优化 接口性能优化有哪些常见手段？ 缓存、SQL、异步、批量
3 定位 如何定位接口慢在数据库、远程调用还是代码逻辑？ 日志、链路追踪、监控

1. 一个接口响应很慢，你怎么排查？

【答】
我会先确认慢是偶发还是持续，再按链路拆开看：

网关耗时
→ 应用接口耗时
→ 数据库耗时
→ Redis 耗时
→ MQ 耗时
→ 第三方接口耗时
→ JVM 和机器资源

【展开】 排查顺序：

步骤 看什么
1 看接口日志，请求量、耗时、错误码是否异常
2 看链路追踪，慢在哪个服务或哪个方法
3 看慢 SQL，是否数据库拖慢
4 看远程调用，是否下游接口超时
5 看 Redis / MQ，是否连接慢或堆积
6 看 JVM，是否 Full GC、线程池打满、CPU 高

面试表达：

接口慢不能直接猜是数据库问题。
我会先通过日志和链路追踪把耗时拆出来，定位是数据库、远程调用、缓存、线程池、GC 还是代码逻辑，再针对性优化。

一句话总结：

接口慢先拆链路，再看证据，最后优化瓶颈点。

2. 接口性能优化有哪些常见手段？

【答】
常见优化手段可以分几类：

方向 手段
数据库 加索引、改 SQL、分页优化、减少大事务
缓存 Redis 缓存热点数据、本地缓存
远程调用 减少调用次数、并行调用、设置超时
代码逻辑 减少循环查库、批量处理、避免重复计算
异步化 非核心逻辑丢 MQ 或线程池
架构 限流、降级、读写分离、拆服务

【展开】 例子：

原来循环 100 次查数据库。
优化成一次批量查询。
原来每次都查商品详情。
优化成热点商品走 Redis 缓存。
原来查用户、查订单、查优惠券串行执行。
如果互不依赖，可以用 CompletableFuture 并行编排。

面试注意：

不要一说性能优化就只说加缓存。
加缓存会带来缓存一致性、穿透、击穿、雪崩等问题，必须结合业务读写特点判断。

一句话总结：

接口优化常见方向是少查、快查、并行查、缓存查、异步做。

3. 如何定位接口慢在数据库、远程调用还是代码逻辑？

【答】
核心是给关键节点打耗时日志，或者使用链路追踪工具看每一段耗时。

【展开】 可以把接口拆成：

Controller 接收请求
Service 业务处理
数据库查询
Redis 查询
Feign 远程调用
结果组装

每一段记录耗时：

queryUser cost=20ms
queryOrder cost=800ms
callCouponService cost=100ms
buildResponse cost=5ms

这样一眼能看出慢点在 queryOrder。

常用工具：

工具 作用
日志埋点 看关键步骤耗时
SkyWalking / Zipkin 看服务调用链路
Arthas trace 看某个方法内部耗时
MySQL slow log 看慢 SQL
Prometheus / Grafana 看系统指标趋势

一句话总结：

定位慢接口要把总耗时拆成多段，哪段耗时高就优化哪段。

7.2 高并发架构设计场景

总览 高并发不是只靠加机器，而是从入口、缓存、服务、数据库、消息队列多层拆压。

序号 题型 面试题 重点
1 设计 高并发系统你会从哪些层面设计？ 分层抗压
2 设计 秒杀系统怎么设计？ 预热、限流、扣库存、异步
3 场景 高并发下如何削峰填谷？ MQ、限流、异步

动画辅助：动画/11-架构.html →「01 架构演变」「02 并发架构设计」

1. 高并发系统你会从哪些层面设计？

【答】
高并发系统要分层设计：

入口层限流
→ 缓存层抗读
→ 服务层无状态扩容
→ MQ 异步削峰
→ 数据库层减少写压力
→ 监控告警兜底

【展开】

层面 方案
网关入口 限流、鉴权、黑名单、验证码
缓存 Redis 缓存热点数据、本地缓存
服务 无状态部署、水平扩容、线程池隔离
MQ 异步处理、削峰填谷
数据库 索引优化、分库分表、读写分离
稳定性 熔断、降级、监控、压测

面试表达：

高并发设计不能只说加 Redis 或加 MQ。
要先明确流量入口、读写比例、热点数据、核心链路和可降级功能，再分层设计。

一句话总结：

高并发靠分层抗压：入口限流、缓存抗读、MQ 削峰、数据库减压、监控兜底。

2. 秒杀系统怎么设计？

【答】
秒杀系统核心是：少让请求打到数据库，先在入口和缓存层挡住大部分压力。

常见设计：

活动预热
→ 网关限流
→ Redis 预扣库存
→ 防重复下单
→ MQ 异步创建订单
→ 数据库最终落库

【展开】

flowchart TB A["用户抢购"] --> B["网关限流"] B --> C["校验资格/防刷"] C --> D["Redis 预扣库存"] D --> E["发送 MQ"] E --> F["异步创建订单"] F --> G["数据库落库"]

关键点：

问题 方案
流量太大 网关限流、验证码、防刷
库存超卖 Redis 原子扣减、数据库乐观锁
重复下单 用户维度幂等，一人一单
数据库压力大 MQ 异步落单
下游异常 限流、降级、失败补偿

一句话总结：

秒杀设计核心是前面挡流量，中间用 Redis 抗库存，后面用 MQ 慢慢落库。

3. 高并发下如何削峰填谷？

【答】
削峰填谷就是把瞬时高峰流量变成后端可以慢慢处理的平稳流量。

常用方案：

MQ 异步化
限流
排队
批量处理
降级非核心功能

【展开】 例子：

用户提交订单后，不直接同步完成所有操作。
先快速校验并写入消息队列。
后端消费者按能力慢慢创建订单、扣库存、发通知。

好处：

前端请求快速返回。
后端按消费能力处理。
数据库不会被瞬时流量打爆。

注意：

用了 MQ 后要考虑消息丢失、重复消费、顺序、补偿和最终一致性。

一句话总结：

削峰填谷就是用队列、限流和异步，把瞬时压力变成可控压力。

7.3 幂等设计场景

总览 幂等解决的是：同一个请求执行多次，结果不能出错。

序号 题型 面试题 重点
1 是什么 什么是幂等？哪些场景必须做幂等？ 重复请求
2 方案 接口幂等有哪些实现方式？ token、唯一键、状态机
3 场景 支付回调如何保证幂等？ 回调重复、订单状态

动画辅助：动画/11-架构.html →「03 幂等设计方案」

1. 什么是幂等？哪些场景必须做幂等？

【答】
幂等就是同一个操作执行一次和执行多次，最终结果一致。

必须做幂等的场景：

下单
支付回调
退款
扣库存
发优惠券
MQ 消费
第三方接口回调

【展开】 为什么会重复？

用户重复点击。
网络超时后客户端重试。
MQ 重复投递。
第三方平台重复回调。
服务超时重试。

面试表达：

只要一个操作重复执行会造成脏数据或资损，就必须做幂等。
比如支付回调重复执行，不能重复修改余额或重复发货。

一句话总结：

幂等就是防止重复请求把业务重复执行。

2. 接口幂等有哪些实现方式？

【答】
常见幂等方案：

方案 适合场景
唯一索引 防止重复插入，比如订单号唯一
token 机制 防止表单重复提交
Redis 去重 短时间防重复请求
状态机 订单状态只能按规则流转
乐观锁 更新时校验版本号
消息去重表 MQ 消费幂等

【展开】 唯一索引：

订单号唯一。
同一个订单号重复插入，数据库直接拒绝。

状态机：

订单只能从 未支付 -> 已支付。
如果已经是已支付，再收到支付成功回调，就直接返回成功，不重复处理。

Redis 去重：

请求带 requestId。
第一次 setnx 成功，执行业务。
后续相同 requestId 直接拒绝或返回已处理。

一句话总结：

幂等没有固定一种方案，核心是给请求或业务动作一个唯一身份，再保证重复执行不会改变结果。

3. 支付回调如何保证幂等？

【答】
支付回调必须做幂等，因为支付平台可能重复通知。

常见做法：

先验签
→ 根据支付单号查订单
→ 判断订单状态
→ 未支付才更新为已支付
→ 已支付直接返回成功

【展开】 关键点：

步骤 说明
验签 确认回调真来自支付平台
查单 根据订单号或支付流水号查订单
状态判断 已支付就不要重复处理
原子更新 使用状态条件更新，比如 where status=‘未支付’
记录流水 保存支付流水，方便对账

SQL 思路：

update orders
set status = 'PAID'
where order_no = ? and status = 'UNPAID'

如果影响行数是 1，说明本次成功处理。

如果影响行数是 0，说明订单可能已经处理过。

一句话总结：

支付回调幂等的核心是验签、查状态、按状态原子更新，已支付的回调直接返回成功。

7.4 线上排错定位场景

总览 线上排错的原则是：先保现场，再看监控，再定位根因。

序号 题型 面试题 重点
1 排查 线上接口突然变慢，你怎么排查？ 监控、日志、链路
2 排查 线上 CPU 飙高怎么定位？ top、jstack、Arthas
3 排查 线上 OOM 怎么定位？ dump、GC、Arthas

1. 线上接口突然变慢，你怎么排查？

【答】
我会先判断范围：

是单个接口慢，还是全站都慢？
是单个实例慢，还是所有实例都慢？
是刚发布后慢，还是流量上涨后慢？

【展开】 排查顺序：

方向 看什么
发布 最近是否上线新版本
流量 QPS 是否突增
应用 CPU、内存、GC、线程池
数据库 慢 SQL、连接池、锁等待
Redis 慢命令、大 key、连接数
MQ 消费堆积、消费者异常
下游 Feign 调用是否超时

面试表达：

线上慢接口要先止血，比如限流、降级、回滚或扩容。
然后通过监控、日志、链路追踪定位慢点，最后修复根因。

一句话总结：

线上变慢先判断影响范围，再止血，再用监控和链路证据定位。

2. 线上 CPU 飙高怎么定位？

【答】
CPU 高要定位到具体线程，再定位到线程栈。

传统方式：

top
top -Hp <pid>
printf "%x\n" <tid>
jstack <pid> > thread.txt

然后在 thread.txt 里搜索：

nid=0x线程ID十六进制

【展开】 Arthas 方式：

dashboard
thread -n 5
thread <线程ID>

常见原因：

死循环
频繁 GC
复杂计算
大量 JSON 序列化
锁竞争导致线程反复争抢

面试表达：

CPU 高不能只说重启。
要先找到哪个 Java 线程占 CPU，再看线程栈定位到具体方法，最后判断是业务死循环、频繁 GC 还是计算逻辑过重。

一句话总结：

CPU 高的关键是从进程定位到线程，再从线程定位到代码栈。

3. 线上 OOM 怎么定位？

【答】
OOM 要先判断是哪类 OOM，再保留现场。

常见类型：

Java heap space
Metaspace
Direct buffer memory
unable to create new native thread
OOMKilled

【展开】 传统方式：

jps
jstat -gc <pid> 1000
jmap -histo:live <pid>
jmap -dump:format=b,file=oom.hprof <pid>

Arthas 方式：

dashboard
jvm
heapdump /tmp/oom.hprof

建议提前配置：

-XX:+HeapDumpOnOutOfMemoryError
-XX:HeapDumpPath=/data/dump

分析思路：

看 dump 里哪些对象最多。
看哪些对象占内存最大。
看谁一直引用着这些对象。
判断是内存泄漏，还是流量太大、对象太大、参数太小。

一句话总结：

OOM 不要先加内存，先看类型和 dump，找到对象增长和引用链。

7.5 项目中线程池使用场景

总览 项目里线程池不是为了“显得高级”，而是为了控制并发、隔离任务、保护系统。

序号 题型 面试题 重点
1 场景 项目中为什么要用线程池？ 复用线程、控制并发
2 参数 线程池参数怎么设置？ CPU / IO / 下游能力
3 监控 如何监控线程池？ active、queue、reject

动画辅助：动画/11-架构.html →「04 线程池底层原理」

1. 项目中为什么要用线程池？

【答】
线程池主要解决三个问题：

  1. 复用线程，减少创建销毁成本。
  2. 控制线程数量，避免线程无限增长。
  3. 隔离不同任务，防止一个慢任务拖垮整个系统。

【展开】 适合用线程池的场景：

异步发送短信、邮件、站内信。
并行调用多个下游接口。
异步写日志或埋点。
后台批处理任务。

不适合乱用：

事务内随便异步。
需要强一致的核心逻辑。
没有超时、没有拒绝策略、没有监控的任务。

一句话总结：

线程池是为了可控地并发执行任务，不是为了把所有逻辑都异步化。

2. 线程池参数怎么设置？

【答】
线程池参数不能只背公式，要看任务类型和下游承载能力。

常见思路：

CPU 密集型：线程数接近 CPU 核数。
IO 密集型：线程数可以适当大一些。
但最终要结合压测、响应时间、下游容量来定。

【展开】 关键参数：

参数 说明
corePoolSize 核心线程数
maximumPoolSize 最大线程数
workQueue 队列大小
keepAliveTime 空闲线程存活时间
handler 拒绝策略

注意：

队列不要无界。
线程数不要无限大。
拒绝策略必须明确。
线程名称要可识别，方便排查。

面试表达：

线程池参数要根据任务是 CPU 密集还是 IO 密集来估算，再结合压测调整。
同时要考虑数据库连接池、HTTP 连接池、下游服务限流，否则线程池调大可能把下游打挂。

一句话总结：

线程池参数看任务类型、机器资源、下游容量和压测结果，不是套一个固定公式。

3. 如何监控线程池？

【答】
线程池至少要监控这些指标：

指标 说明
activeCount 正在执行任务的线程数
poolSize 当前线程数
corePoolSize 核心线程数
maximumPoolSize 最大线程数
queueSize 队列积压数量
completedTaskCount 已完成任务数
rejectCount 拒绝任务数量

【展开】 重点看：

activeCount 长时间接近 maximumPoolSize。
queueSize 持续上涨。
rejectCount 大于 0。
任务耗时持续变长。

这些通常说明：

线程池处理不过来。
任务执行变慢。
下游服务变慢。
队列堆积风险变大。

面试表达：

项目中线程池一定要有监控和告警。
否则只有等接口超时、任务丢失或系统卡死时，才知道线程池已经打满。

一句话总结：

线程池监控重点是活跃线程、队列积压、拒绝次数和任务耗时。

7.6 数据库优化场景

总览 数据库优化不要只背索引，要从定位、分析、修改、验证四步走。

序号 题型 面试题 重点
1 排查 慢 SQL 怎么定位和优化？ slow log、explain
2 原因 索引失效有哪些常见原因？ 函数、隐式转换、like
3 场景 分页查询很慢怎么优化？ 深分页

1. 慢 SQL 怎么定位和优化？

【答】
慢 SQL 排查流程：

开启慢查询日志
→ 找到慢 SQL
→ 用 explain 看执行计划
→ 分析索引和扫描行数
→ 优化 SQL 或索引
→ 压测验证

【展开】 explain 重点看：

字段 关注点
type 访问类型，尽量避免 ALL
key 实际用到的索引
rows 预估扫描行数
Extra 是否 filesort、temporary

常见优化：

给 where / join / order by 字段建立合适索引。
避免 select *。
减少回表。
大查询拆小。
避免在索引列上使用函数。
分页深时改成基于游标或上一页最大 ID。

一句话总结：

慢 SQL 优化先用慢日志找到问题，再用 explain 看执行计划，最后改 SQL 或索引并验证效果。

2. 索引失效有哪些常见原因？

【答】
常见索引失效原因：

原因 示例
对索引列使用函数 where date(create_time) = ?
隐式类型转换 字符串字段用数字查
左模糊查询 like '%abc'
联合索引不满足最左前缀 (a,b,c) 直接按 b 查
使用 or 不当 两边条件不都有索引
范围查询后面的列无法充分使用 a = ? and b > ? and c = ?
数据区分度太低 性别这类字段单独建索引效果差

【展开】 例子：

select * from user where phone = 13800138000;

如果 phone 是字符串类型，但查询传数字，可能发生隐式转换，影响索引使用。

更稳写法：

select * from user where phone = '13800138000';

面试表达：

索引不是建了就一定会用。
要结合 SQL 写法、字段区分度、联合索引顺序和执行计划判断。

一句话总结：

索引失效常见原因是 SQL 写法破坏了索引有序性或导致 MySQL 无法按索引快速定位。

3. 分页查询很慢怎么优化？

【答】
分页慢通常是深分页问题。

比如：

select * from orders order by id limit 1000000, 20;

MySQL 需要跳过前面 1000000 条，再取 20 条，成本很高。

【展开】 优化方式：

方案 说明
基于上一页最大 ID where id > lastId limit 20
延迟关联 先查主键，再回表查详情
覆盖索引 查询字段尽量从索引直接拿
限制深翻页 产品上限制只能翻前 N 页
搜索引擎 复杂搜索分页交给 ES 等组件

基于 ID 翻页：

select * from orders
where id > 1000000
order by id
limit 20;

延迟关联：

select o.*
from orders o
join (
  select id from orders order by id limit 1000000, 20
) t on o.id = t.id;

一句话总结：

深分页慢是因为跳过的数据太多，优化思路是减少扫描和回表，能用游标翻页就别用大 offset。

3. 你负责的功能从需求到上线是怎么完成的？

通用流程：

理解需求
→ 拆接口和表结构
→ 写代码
→ 自测
→ 前后端联调
→ 提测
→ 修复 Bug
→ 上线
→ 观察日志和监控

【展开】

flowchart TB A["拿到需求"] --> B["确认业务规则"] B --> C["设计接口和表结构"] C --> D["编码实现"] D --> E["本地自测"] E --> F["前后端联调"] F --> G["测试环境提测"] G --> H["修 Bug"] H --> I["上线观察日志和监控"]

示例回答：

以简历解析功能为例，我先和产品确认上传格式、解析字段和失败提示。
然后设计 resume_record 表保存上传记录和解析结果。
接口上提供上传简历、查询解析结果、重新解析三个接口。
开发完成后我用几份不同格式的简历做自测，再和前端联调上传和结果展示。
提测后修复了文件过大、解析失败提示不清晰的问题。

2 高频 数据库表大概多少数据？增长量多少？ 数据规模

1. 项目用户量、日活、QPS 怎么回答？

【答】
这类数字不要乱说。要先讲项目阶段，再讲大概范围。

可以这样答：

我们项目不是千万级大流量，属于中小型业务系统。
日活大概几百到几千。
核心接口平时 QPS 不高，高峰可能几十到一百左右。

【展开】 数字之间要匹配：

说法 是否合理
日活 500，但 QPS 5000 不合理，除非有特殊高频调用
内部管理系统，QPS 几十 合理
C 端秒杀活动，峰值 QPS 上千 可能合理，但要能讲限流、缓存、MQ
小项目说日活百万 风险很大，容易被连续追问打穿

更稳的回答：

准确数字我没有每天统计，但从 Grafana 面板和日志看，日常核心接口 QPS 在几十以内。
活动或批量任务时会有短时峰值，所以我们做了限流、缓存和异步处理。

一句话总结：

项目数字不用吹大，合理、能解释、和架构匹配才最重要。

2. 数据库表大概多少数据？增长量多少？

【答】
回答数据量时，要说清楚是哪张表、当前量级、增长来源和优化方式。

【展开】 示例：

用户表数据不大，大概几万级。
简历解析记录表增长比较快，按上传次数增长，测试环境数据少，生产大概几十万级。
面试记录表按用户模拟面试次数增长，也可能到几十万。
对于高频查询字段，比如 user_id、create_time、status，我们建了联合索引。

面试官可能继续问：

最大的一张表是哪张？
为什么会增长？
有没有做归档？
索引怎么建的？
慢 SQL 怎么处理？

回答思路：

问题 回答重点
最大表 说具体业务表，不要只说 user
增长原因 业务动作产生数据
查询字段 user_id、status、create_time 等
优化方式 索引、分页、归档、冷热数据

一句话总结：

数据量要绑定具体业务表讲，顺带说明为什么增长、怎么查询、怎么优化。

3. 你们项目部署几台机器？配置怎么样？

【答】
部署规模要符合项目体量。中小项目不要硬说几十台机器。

可以这样答：

测试环境通常是单机或少量容器部署。
生产环境按服务拆分部署，核心服务至少 2 个实例，避免单点。
机器配置根据业务规模可能是 2C4G、4C8G 或更高。

【展开】 示例口径：

我们项目生产环境主要是 Docker 部署。
网关、业务服务、Redis、MySQL 分开部署。
核心业务服务一般部署 2 个实例，方便滚动发布和故障切换。
监控使用 Prometheus + Grafana，链路追踪使用 SkyWalking。

面试注意：

如果说用了微服务，却所有服务都只有一个实例，面试官可能追问高可用。
如果说 QPS 很高，却机器配置很低、没有缓存和限流，也容易不可信。

一句话总结：

部署数字要和业务规模、QPS、高可用方案匹配，不要为了显得高级乱报。

4. 接口性能、慢接口、错误率这些数字怎么讲？

【答】
性能数字要讲“平均值 + 高峰值 + 优化前后变化”，这样更真实。

【展开】 示例：

大部分普通查询接口在 100ms 到 300ms。
涉及 AI 调用、文件解析或远程服务的接口会更慢，可能 1 到 3 秒。
简历解析这种任务我们不会让用户一直等同步结果，而是异步处理，前端轮询或刷新查看结果。

常见性能口径：

指标 回答方式
RT 普通接口多少 ms，复杂接口多少秒
错误率 正常很低，异常时通过日志和监控定位
慢接口 说明哪个接口慢，为什么慢，怎么优化
优化效果 优化前后对比，比如 2s 降到 500ms

一句话总结：

性能数字要能解释原因，最好带一个优化前后的真实案例。

9.1 可观测性工具

总览 可观测性工具不要孤立背。记住三句话：

Prometheus 负责采集指标。
Grafana 负责展示指标。
SkyWalking 负责看调用链路。
序号 题型 面试题 重点
1 是什么 SkyWalking 是什么？线上接口慢怎么用它定位？ 链路追踪
2 是什么 Prometheus 和 Grafana 分别是干什么的？ 指标采集与展示
3 场景 服务报警后，你怎么结合监控、链路和日志排查？ 排查闭环

1. SkyWalking 是什么？线上接口慢怎么用它定位？

【答】
SkyWalking 是链路追踪工具，用来查看一次请求经过了哪些服务、每个服务耗时多少、哪里报错。

接口变慢时，先用 SkyWalking 找出慢的是哪个服务、哪个接口、哪个 SQL 或远程调用。

【展开】 一次请求可能经过：

网关
→ 订单服务
→ 用户服务
→ 库存服务
→ 数据库
→ Redis

SkyWalking 可以把这条链路串起来：

flowchart TB A["用户请求"] --> B["Gateway"] B --> C["订单服务"] C --> D["用户服务"] C --> E["库存服务"] C --> F["MySQL / Redis"] D --> G["查看每一段耗时和异常"] E --> G F --> G

排查时重点看：

看什么 说明
Trace 一次请求完整链路
Span 耗时 哪个服务、哪个方法最慢
错误标记 哪个节点报错
SQL / RPC 调用 慢在数据库还是下游服务

一句话总结：

SkyWalking 解决的是“请求慢在哪里”的问题，重点看调用链路和每一段耗时。

2. Prometheus 和 Grafana 分别是干什么的？

【答】
Prometheus 负责采集和存储指标，Grafana 负责把指标做成可视化面板。

简单说：

Prometheus 像数据采集器。
Grafana 像监控大屏。

【展开】 常见监控指标：

指标 用来判断什么
CPU 使用率 机器或容器是否计算压力大
内存使用率 是否存在内存上涨、OOM 风险
磁盘使用率 日志或数据文件是否快写满
QPS 请求量是否突增
RT / 响应时间 接口是否变慢
错误率 是否大量 5xx 或业务异常
JVM GC 是否频繁 GC、Full GC
线程池指标 是否线程打满、队列堆积
flowchart LR A["应用 / 机器 / 容器暴露指标"] --> B["Prometheus 采集"] B --> C["Grafana 展示面板"] C --> D["告警 / 趋势分析"]

一句话总结：

Prometheus 管指标数据，Grafana 管图形展示；排错时先看趋势，再结合日志和链路定位原因。

3. 服务报警后，你怎么结合监控、链路和日志排查？

【答】
我会按“指标 → 链路 → 日志 → 命令 → 修复”的顺序排查。

【展开】 排查顺序：

步骤 看什么
1 Grafana 看 CPU、内存、QPS、RT、错误率是否异常
2 Prometheus 看具体指标和告警规则
3 SkyWalking 看慢请求或错误链路
4 应用日志看异常堆栈、请求参数、错误码
5 Linux / Docker 看机器和容器状态
6 判断是否需要限流、降级、回滚、扩容

面试表达：

不能只说看日志。
线上排错要先用指标判断范围，再用链路定位位置，再用日志确认原因。

一句话总结：

监控告诉你有没有问题，链路告诉你问题在哪一段，日志告诉你具体为什么。

9.2 Linux 排错

总览 Linux 排错不用背很多冷门命令，先掌握高频四类：

CPU
内存
磁盘
端口和日志
序号 题型 面试题 重点
1 排查 Linux 上 CPU 很高怎么排查？ top、线程、日志
2 排查 Linux 上内存占用高怎么排查？ free、top、进程
3 排查 磁盘打满怎么定位？ df、du、日志文件
4 排查 端口不通、服务没响应怎么查？ ss、curl、日志

1. Linux 上 CPU 很高怎么排查？

【答】
先找到哪个进程 CPU 高，再看这个进程为什么高。

常用命令：

top
ps -ef | grep java
top -Hp <pid>

【展开】 如果是 Java 进程 CPU 高，可以继续定位线程：

top -Hp <pid>
printf "%x\n" <线程ID>
jstack <pid> > thread.txt

然后在 thread.txt 里找对应的 nid=0x线程ID。

常见原因：

死循环。
大量计算。
频繁 Full GC。
锁竞争严重。
日志打印过多。

一句话总结：

CPU 高要从机器定位到进程，再从进程定位到线程，最后从线程栈定位到代码。

2. Linux 上内存占用高怎么排查？

【答】
先看系统内存，再找占内存最高的进程。

常用命令：

free -h
top
ps aux --sort=-%mem | head

【展开】 如果是 Java 服务内存高，继续看 JVM：

jstat -gc <pid> 1000
jmap -histo:live <pid> | head

排查重点：

现象 可能原因
Java heap 持续上涨 对象没有释放、缓存无上限
Full GC 频繁 堆压力大、对象晋升过快
native 内存高 直接内存、线程数过多
容器 OOMKilled 容器内存限制太小或程序内存泄漏

一句话总结：

内存高先分清是系统内存、JVM 堆内存，还是容器限制导致的问题。

3. 磁盘打满怎么定位？

【答】
先看哪个磁盘分区满了，再找哪个目录或文件最大。

常用命令：

df -h
du -sh /* 2>/dev/null
du -sh /var/log/* 2>/dev/null

【展开】 常见原因：

应用日志没有切割。
Docker 日志过大。
临时文件没有清理。
上传文件或导出文件堆积。
数据库文件增长过快。

注意：

不要上来就乱删文件。
生产环境先确认文件用途，再压缩、清理或做日志切割。

一句话总结：

磁盘满先用 df 找分区，再用 du 找大目录，最常见原因是日志没有治理。

4. 端口不通、服务没响应怎么查？

【答】
先确认服务有没有启动，再看端口有没有监听，最后看网络和日志。

常用命令：

ss -lntp
curl -v http://127.0.0.1:8080/actuator/health
tail -n 200 app.log

【展开】 排查顺序：

进程是否存在。
端口是否监听。
本机访问是否正常。
容器端口是否映射。
防火墙或安全组是否放行。
应用日志是否启动失败。

一句话总结：

端口不通不要只猜网络问题，先看进程、端口、本机访问、容器映射和日志。

9.3 Docker 排错

总览 Docker 排错重点看四件事：

容器有没有起来
日志报了什么
资源是否够
端口和网络是否正确
序号 题型 面试题 重点
1 排查 Docker 容器启动失败怎么排查？ ps、logs、inspect
2 排查 Docker 容器 CPU 或内存异常怎么查？ stats、limits
3 排查 Docker 端口访问不通怎么排查？ 端口映射、监听地址
4 排查 Docker 日志太大或磁盘占满怎么办？ 日志驱动、清理策略

1. Docker 容器启动失败怎么排查？

【答】
先看容器状态，再看启动日志和容器配置。

常用命令：

docker ps -a
docker logs <container>
docker inspect <container>

【展开】 常见原因：

原因 表现
启动命令写错 容器马上退出
环境变量缺失 日志里配置为空或连接失败
端口冲突 bind 端口失败
镜像版本不对 类、命令或依赖不存在
挂载路径错误 文件找不到或权限不足

一句话总结：

容器启动失败先看 docker ps -a 和 docker logs，大多数原因都能从日志里看到。

2. Docker 容器 CPU 或内存异常怎么查？

【答】
用 docker stats 看容器资源，再结合应用监控判断是否是程序问题。

常用命令：

docker stats
docker inspect <container>

【展开】 重点看：

指标 说明
CPU % 容器 CPU 是否持续很高
MEM USAGE / LIMIT 内存是否接近限制
NET I/O 网络流量是否异常
BLOCK I/O 磁盘读写是否异常

如果容器被杀掉，可以看：

docker inspect <container> | grep -i oom

一句话总结：

Docker 资源异常先看 stats，再判断是容器限制太小，还是应用本身 CPU、内存、IO 有问题。

3. Docker 端口访问不通怎么排查？

【答】
先看端口有没有映射，再看容器内服务有没有监听。

常用命令：

docker ps
docker port <container>
docker exec -it <container> sh
ss -lntp

【展开】 常见问题：

启动容器时没有 -p 端口映射。
应用只监听 127.0.0.1，没有监听 0.0.0.0。
宿主机端口被防火墙拦截。
容器启动了，但应用实际启动失败。
访问的端口和映射端口搞反。

例子：

docker run -p 8080:8080 app:latest

这里前面的 8080 是宿主机端口，后面的 8080 是容器端口。

一句话总结：

Docker 端口不通重点看端口映射、应用监听地址、宿主机网络和容器日志。

4. Docker 日志太大或磁盘占满怎么办？

【答】
先确认是不是容器日志占满磁盘，再做日志限制和清理。

常用命令：

docker system df
docker logs --tail 200 <container>

【展开】 Docker 默认日志可能持续增长。生产环境要配置日志轮转，例如：

{
  "log-driver": "json-file",
  "log-opts": {
    "max-size": "100m",
    "max-file": "3"
  }
}

排查和治理：

看 docker system df 判断镜像、容器、日志占用。
给 Docker 配置日志大小限制。
应用日志也要按天切割。
清理无用镜像和停止的容器前，要确认不会影响服务。

一句话总结：

Docker 日志不能无限写，生产环境一定要配置日志轮转，否则很容易把磁盘打满。

9.4 ELK 分布式日志分析

总览 ELK 解决的是：服务多了以后，日志分散在不同机器和容器里，怎么统一收集、搜索和分析。

单体项目时，登录一台机器看日志还能接受。微服务和容器化以后，请求可能经过多个服务：

Gateway
→ 用户服务
→ 订单服务
→ 库存服务
→ 支付服务

如果每个服务日志都在不同机器上，靠人工一台台登录查日志，效率很低。所以企业里常用 ELK 或类似方案做集中日志分析。

序号 题型 面试题 重点
1 是什么 ELK 是什么？各组件分别负责什么？ Elasticsearch、Logstash、Kibana
2 场景 线上报错时，怎么用 ELK 快速定位问题？ traceId、关键字、时间范围
3 场景 日志太多、查不到日志、日志不规范怎么处理？ 日志规范与治理

1. ELK 是什么？各组件分别负责什么？

【答】
ELK 是一套常见的日志收集和分析方案，主要由 Elasticsearch、Logstash、Kibana 组成。

简单理解：

Logstash 负责采集和处理日志。
Elasticsearch 负责存储和搜索日志。
Kibana 负责可视化查询和展示日志。

实际项目里也经常用 Filebeat 采集日志，再发送到 Logstash 或 Elasticsearch。

【展开】

flowchart LR A["应用服务产生日志"] --> B["Filebeat / Logstash 采集"] B --> C["Elasticsearch 存储和检索"] C --> D["Kibana 查询和展示"]

看图重点：ELK 的主线是“应用产生日志 → Logstash/Filebeat 采集 → Elasticsearch 存储检索 → Kibana 查询展示”。

组件作用：

组件 作用
Elasticsearch 存日志、建索引、支持快速搜索
Logstash 收集、过滤、转换日志
Kibana 提供页面查询、图表、日志分析
Filebeat 轻量级日志采集器，常部署在服务器或容器节点

一句话总结：

ELK 的核心价值是把分散日志集中起来，让我们可以按时间、服务、关键字、traceId 快速检索。

2. 线上报错时，怎么用 ELK 快速定位问题？

【答】
我会先确定报错时间、服务名、接口路径、traceId，再到 Kibana 里检索相关日志。

常用检索条件：

时间范围
服务名
traceId / requestId
接口路径
错误关键字
用户 id / 订单号

【展开】 排查流程：

用户反馈或监控告警
→ 确定大概时间范围
→ 根据 traceId 或接口路径查日志
→ 看异常堆栈和上下文参数
→ 结合 SkyWalking 看链路
→ 判断是代码异常、下游超时、数据库问题还是参数问题
flowchart TB A["线上报错"] --> B["确定时间范围"] B --> C["Kibana 搜 traceId / 服务名 / 接口"] C --> D["查看异常堆栈"] D --> E["结合 SkyWalking 看链路"] E --> F["定位具体服务和代码位置"]

看图重点：Kibana 的价值不是“看日志页面”，而是按时间、索引、关键字、traceId 快速缩小问题范围。

面试表达：

分布式系统排错时，traceId 很关键。
一次请求跨多个服务，只要日志里都打印同一个 traceId，就可以在 ELK 里把这次请求的上下游日志串起来。

一句话总结：

ELK 排错的核心是用时间范围、服务名、关键字和 traceId 把一次请求的日志串起来。

3. 日志太多、查不到日志、日志不规范怎么处理？

【答】
日志治理要从采集、格式、级别、保留时间和字段规范几方面处理。

【展开】 常见问题：

问题 处理方式
日志太多 控制 debug 日志，区分 info、warn、error
查不到日志 检查采集路径、索引、服务名、时间范围
日志没上下文 打印 traceId、userId、orderNo 等关键字段
日志格式乱 统一 JSON 格式或统一日志模板
ES 存储压力大 设置索引生命周期，定期归档或删除旧日志

推荐日志内容：

时间
服务名
环境
traceId
接口路径
业务关键字段
错误码
异常堆栈
耗时

不要这样打日志：

处理失败。

更好的方式：

resume parse failed, traceId=xxx, userId=1001, fileId=2002, reason=AI_TIMEOUT

一句话总结：

日志不是越多越好，而是要能在出问题时用关键字段快速还原现场。
